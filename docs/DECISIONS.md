# Журнал решений

Этот файл дополняется при принятии существенных архитектурных или продуктовых решений.

## ADR-001: Backend-first и Swagger

**Статус:** принято.

Первая версия не имеет frontend. Все возможности доступны и проверяются через OpenAPI/Swagger.

## ADR-002: Python как прикладной слой, C++ как вычислительное ядро

**Статус:** принято.

FastAPI отвечает за HTTP, импорт, валидацию, БД и orchestration. C++ используется только для чистых вычислений после стабилизации контракта и подключается через pybind11.

## ADR-003: Точный ledger как источник истины

**Статус:** принято.

Позиции и метрики вычисляются из операций. Текущий баланс источника может использоваться как контрольный snapshot, но не заменяет историю.

## ADR-004: Двухфазный импорт

**Статус:** принято.

Файл сначала разбирается в staging и preview. Ledger изменяется только после подтверждения. Подтверждение идемпотентно, импорт можно откатить.

## ADR-005: Адаптеры исходных форматов

**Статус:** принято.

Пользователь загружает поддерживаемый отчёт без ручного преобразования. Универсальные CSV/XLSX-шаблоны являются fallback. Каждый банковский, брокерский, CEX или PDF-формат имеет отдельный версионированный адаптер.

## ADR-006: PDF не считается автоматически полным источником

**Статус:** принято.

Документы классифицируются по полноте. Аналитический PDF с агрегатами не преобразуется в вымышленные сделки. Пользователь получает предупреждение о границах импорта.

## ADR-007: Ограниченное риск-ориентированное тестирование

**Статус:** принято.

Цели полного покрытия нет. Проверяются только финансовая точность, критичные инварианты, импорт, дедупликация, rollback и основные сквозные сценарии.

## ADR-008: Python 3.13 и воспроизводимое окружение uv

**Статус:** принято.

Первая фаза закреплена на Python 3.13. Прямые и транзитивные Python-зависимости
фиксируются в `uv.lock`; локальная установка и контейнерная сборка используют
`uv sync --locked`. В Docker закреплён `uv` 0.11.32, устанавливаемый из PyPI,
чтобы сборка не зависела от доступности отдельного container registry.

Последствия: окружение воспроизводимо между локальной разработкой и контейнером;
переход на следующую версию Python выполняется отдельным проверяемым изменением.

## ADR-009: Async psycopg, readiness и миграции локального API

**Статус:** принято.

SQLAlchemy использует async-интерфейс psycopg 3. `/health/live` проверяет только
работоспособность процесса, а `/health/ready` выполняет минимальный `SELECT 1` в
PostgreSQL. При локальном контейнерном запуске API применяет `alembic upgrade head`
до старта Uvicorn.

Последствия: оркестратор различает живой и готовый к работе процесс, а локальная
схема автоматически достигает ожидаемой revision. Для production способ запуска
миграций должен быть пересмотрен отдельно, чтобы несколько реплик не управляли
схемой одновременно.

## ADR-010: Точностные контракты первой версии

**Статус:** принято.

Money, Quantity и Price используют Python `Decimal` и PostgreSQL `NUMERIC(38,18)`;
Rate — `Decimal` и `NUMERIC(38,24)`. Общие типы допускают знак, а допустимость
отрицательного значения определяется конкретной доменной операцией. До передачи в
PostgreSQL значение проверяется, поэтому лишний scale не округляется молча.

На JSON-границе точные значения принимаются и возвращаются только строками в plain
decimal notation. JSON numbers, exponent notation, разделители и не-finite значения
запрещены. Python-mode сохраняет `Decimal`, UUID и timezone-aware `datetime` без
строкового преобразования.

CurrencyCode в первой версии проверяет синтаксис трёх заглавных ASCII-букв, но не
подменяет справочник ISO 4217. AssetIdentifier — канонический lowercase UUID.
Время нормализуется в UTC и хранит отдельный признак исходной точности: date, minute,
second, millisecond или microsecond.

Последствия: изменение пределов требует отдельного решения и миграции. Исходное
представление импортированной строки всё равно сохраняется в import staging, поэтому
нормализованный Decimal не заменяет аудиторский raw value.

## ADR-011: Единый безопасный формат ошибок API

**Статус:** принято.

Ошибки HTTP, Pydantic validation и необработанные исключения возвращаются в envelope
`{"error": {"code", "message", "details"}}`. Detail содержит location, стабильный
машинный code и безопасное сообщение. Ошибочное входное значение и Pydantic input
не копируются в ответ или production-лог.

OpenAPI глобально документирует тот же `ErrorResponse` для 422 и 500; endpoints
добавляют доменные статусы, например 503 readiness, в этом же формате.

Последствия: новые endpoints должны использовать `ApiErrorException` для доменных
HTTP-ошибок, не создавая собственные несовместимые envelopes.

## ADR-012: Справочная модель портфелей, счетов и инструментов

**Статус:** принято.

До появления identity/auth портфель является верхнеуровневым локальным ресурсом API
без фиктивного пользователя или невалидируемого `owner_id`. Будущая identity-фаза
добавит явную связь владельца отдельной миграцией. Портфель хранит обязательную
базовую валюту. Счёт принадлежит одному портфелю и имеет закрытый тип `broker`,
`bank` или `cex`; удаление портфеля каскадно удаляет только его справочные счета.
Будущие ledger-ссылки должны запрещать удаление используемых сущностей.

Инструмент является глобальным справочным активом с типом и валютой оценки.
Внешние идентификаторы хранятся отдельными типизированными строками. `exchange`
является обязательным qualifier для ticker, а `provider` — для provider code;
сами по себе exchange и provider инструмент не идентифицируют. ISIN и crypto asset
code не имеют дополнительного scope. Уникальность обеспечивается PostgreSQL
partial indexes для ISIN, exchange+ticker, provider+provider code и crypto asset
code, а дубликаты внутри одного инструмента запрещены отдельным индексом с
`NULLS NOT DISTINCT`.

Enums хранятся как строки с `CHECK` constraints, а не как PostgreSQL enum types,
чтобы их развитие выполнялось обычными проверяемыми Alembic-миграциями. API
использует UUID, безопасный общий error envelope и ограниченные `limit/offset`
списки. Имена, валюты и qualifier-комбинации проверяются и в Pydantic, и ключевыми
ограничениями БД.

## ADR-013: Неизменяемый ledger и correction operations

**Статус:** принято.

Каноническая операция хранится как неизменяемый relational envelope и типизированный
JSONB payload. Envelope содержит portfolio/account, тип и время операции, точность
исходного времени, источник, audit timestamps, основной instrument для фильтрации и
необязательную ссылку на исправляемую операцию. Связь account+portfolio проверяется
составным внешним ключом PostgreSQL; используемые счета и инструменты удалять нельзя.

Pydantic использует discriminated union для `trade`, `income`, `fee`, `tax`,
`cash_movement`, `currency_exchange`, `crypto_transfer`, `corporate_action`,
`bond_redemption` и `balance_adjustment`. Денежные значения, цены и количества
проходят общие Decimal-контракты до сериализации в JSONB строками. Тип payload
повторно определяется по `operation_type` при чтении.

Существующие операции не обновляются и не удаляются через API. Ошибка исправляется
новой экономически компенсирующей операцией с `correction_of_operation_id` и
обязательной audit-note. Оригинал сохраняется для трассировки, а расчётное ядро в
дальнейшем учитывает обе записи. Ручной API всегда выставляет источник `manual`;
поля import source уже присутствуют в envelope, но будут заполняться только
атомарным confirm из импортного модуля.

## ADR-014: Нормализованный staging импорта и границы удаления

**Статус:** принято.

`ImportBatch` принадлежит одной согласованной паре portfolio/account, хранит
метаданные исходного файла, внутренний storage key, SHA-256, классификацию полноты,
статус, счётчики и безопасную сводку ошибок. Повторный SHA-256 на одном account
защищён уникальным индексом; сервис загрузки должен возвращать существующий batch,
а не обходить это ограничение.

`ImportRow` хранит raw JSON отдельно от normalized operation candidate, источник
строки, диагностику, статус, будущий fingerprint и необязательную ссылку на
созданную ledger operation. `ImportResolution` принадлежит конкретной строке и
фиксирует тип решения, источник user/adapter и типизированный JSON payload.
Пара row+batch защищена составным внешним ключом.

Удаление неподтверждённого batch каскадно удаляет только staging rows и resolutions.
Если строка уже связана с ledger operation, `RESTRICT` запрещает потерю
трассировки. `operations.import_batch_id` теперь имеет внешний ключ на batch, а
любая import source operation обязана иметь batch. Подтверждение, rollback и
экономическое удаление операций остаются отдельным процессом раздела 7.

Enums хранятся строками с `CHECK` constraints. Поля raw/candidate/diagnostics
используют PostgreSQL JSONB, но полные raw строки нельзя выводить в production-логи
или error responses.

API и Alembic явно загружают единый registry доменных моделей. Это необходимо,
потому что ledger и import staging имеют взаимные внешние ключи, а корректность
SQLAlchemy metadata не должна зависеть от порядка импортов модулей или test
collection.

## ADR-015: Локальное ObjectStorage, upload API и PostgreSQL worker

**Статус:** принято.

Исходные файлы первой фазы хранятся через интерфейс `ObjectStorage`. Локальная
реализация использует отдельный каталог вне project tree и отдельный Docker volume.
Путь формируется только из случайного server-generated key; пользовательское имя
сохраняется как очищенное metadata и никогда не участвует в пути. Размер ограничен
на потоковой записи, файлы создаются с закрытыми permissions. До сохранения
проверяются declared format, allowlist расширения/content type и базовая сигнатура;
перед worker parse повторно сверяются размер и SHA-256.

`POST /api/v1/imports` принимает multipart upload. Новый batch возвращается с HTTP
201. Если тот же SHA-256 уже существует на том же account, временная копия
удаляется, а API возвращает существующий batch с HTTP 200 и `duplicate=true`.
Уникальный индекс account+SHA-256 остаётся последней защитой от конкурентной гонки.
Public responses не содержат storage key. Raw rows доступны только через явные
preview/rows endpoints и не попадают в error responses или production-логи.

Адаптеры регистрируются по неизменяемой паре format ID + version. Registry выдаёт
только адаптеры заявленного типа файла; adapter возвращает detection, parsed rows и
validation diagnostics, но не пишет в ledger. Неподдерживаемый upload завершается
безопасным failed status. Первым зарегистрированным адаптером стал
`universal_broker` версии `1.0`.

Очередь worker хранится в PostgreSQL `import_jobs`. Claim выполняется через
`FOR UPDATE SKIP LOCKED`, фиксирует worker ID, lock time и число попыток. Worker
проверяет целостность файла, вызывает detect/parse/validate, атомарно заменяет
staging rows и сохраняет только безопасную диагностику. API и worker используют
общий storage volume. Это сохраняет простую инфраструктуру первой версии без
Redis, RabbitMQ или Celery.

## ADR-016: Universal broker CSV v1 и сопоставление инструментов

**Статус:** принято.

Формат `universal_broker` версии `1.0` использует UTF-8 CSV с автоматически
определяемым разделителем и явными колонками `Quantity`, `Price` и `Amount`.
`Amount` предназначен только для income, standalone fee/tax и cash movement, поэтому
цена и количество не перегружаются несвязанными значениями. Направление задаётся
`Type`, а входное числовое значение нормализуется как точный положительный модуль.

Одна исходная строка может создать несколько staging rows: основную операцию и
отдельные fee/tax. Все они сохраняют одинаковый `source_row_number` и полную raw
строку, но получают собственный sequence number и канонический payload. Это
сохраняет разделение типов ledger без потери трассировки к исходной строке.

Адаптер остаётся детерминированным парсером без доступа к PostgreSQL. Сопоставление
выполняется отдельным шагом processor: сначала ISIN, затем точное
exchange+ticker+currency. Неизвестный инструмент не создаётся, конфликтующие
идентификаторы становятся ошибкой, а неизвестный match остаётся warning-кандидатом
с исходной ссылкой для будущего explicit resolution. Preview агрегирует только
ready/warning candidates и возвращает точные суммы по валютам без расчёта trade
notional.

Последствия: confirm раздела 7 должен принимать только полностью канонические
кандидаты или применённые explicit resolutions; кандидаты с `instrument_reference`
не могут молча попасть в ledger.

## ADR-017: Дедупликация, атомарный confirm и границы rollback

**Статус:** принято.

У импортной ledger operation хранятся два разных SHA-256 значения. `fingerprint` —
стабильная каноническая идентичность, по которой будущие загрузки находят возможный
дубль. `deduplication_key` — уникальный ключ записи в пределах account. Обычно они
равны, но после явного `allow_duplicate` ключ детерминированно дополняется scope
batch/row, а исходный fingerprint сохраняется. Один уникальный fingerprint не
подходит для обеих задач: его замена после разрешения дубля сделала бы такой дубль
невидимым для следующих импортов.

Если источник дал external ID, канонический fingerprint включает account,
source provider, external ID и operation type. Последнее разделяет trade, fee и
tax, созданные из одной исходной строки. При отсутствии external ID fingerprint
строится из точного времени, типа, payload и note. SHA-256 файла отдельно защищает
от повторной загрузки полностью одинакового документа.

Confirm выполняется синхронно в одной PostgreSQL-транзакции. Batch и staging rows
блокируются `FOR UPDATE`, все кандидаты повторно валидируются до записи, а уникальный
partial index account+deduplication key остаётся защитой от конкурентной гонки.
Повторный confirm уже committed/completed batch не создаёт записи, а возвращает
сохранённые operation IDs.

Rollback физически удаляет только операции с `import_batch_id` выбранного batch,
обнуляет row links и возвращает строки в состояние review. Исходный файл, raw rows
и resolutions сохраняются; ручные операции и другие batch не затрагиваются.
Rollback повторяем и запрещён, если correction operation уже ссылается на одну из
удаляемых операций, чтобы не разрушать историю исправлений.

Последствия: recalculation остаётся следующим отдельным шагом раздела 8. До его
появления успешный confirm завершает batch в состоянии `committed`.

## ADR-018: Weighted-average расчёт и заменяемый snapshot позиций

**Статус:** принято.

Расчётное ядро имеет чистый синхронный контракт
`operations + prices + cost basis policy -> positions + cash + metrics + diagnostics`.
Оно не знает о FastAPI, SQLAlchemy, файлах импорта и фоновых задачах. Входные
operations сортируются по `occurred_at` и UUID, поэтому результат не зависит от
порядка выборки. Контракт использует только UUID, timezone-aware datetime,
`Decimal`, типизированные operation payloads и простые неизменяемые структуры.

Первой и пока единственной cost-basis policy выбрана `weighted_average`. Покупка
увеличивает количество и общую себестоимость, продажа списывает пропорциональную
часть текущей себестоимости. Realised P&L считается как proceeds минус списанная
себестоимость; unrealised P&L — market value минус оставшаяся себестоимость.
Комиссии и налоги не капитализируются и не вычитаются скрыто из торгового P&L:
fees, taxes и income сохраняются отдельными метриками по account и currency.

Произведение quantity на price, пропорциональное списание себестоимости и другие
производные Money округляются только явным `ROUND_HALF_EVEN` до 18 дробных знаков.
Вычисления выполняются в расширенном Decimal-контексте, а результат повторно
проверяется контрактом `NUMERIC(38,18)`. Это исключает случайное округление
стандартным Decimal context или PostgreSQL.

Ручные market prices хранятся как точные versioned observations. Для snapshot с
заданным `as_of` берётся последняя цена инструмента в подходящей валюте не позднее
этого момента. Snapshot является производным и заменяемым: на портфель хранится
один текущий результат, а позиции, cash balances и currency metrics полностью
заменяются одной транзакцией. Ledger и price observations при этом не изменяются.

Отрицательная позиция, отсутствие цены, неизвестная себестоимость transfer или
adjustment, а также несовпадение валют не маскируются нулём. Расчёт сохраняет
структурированную diagnostic и оставляет невычислимые P&L-поля `null`. CEX trade в
текущем ledger представлен инструментом и денежной quote-ногой `price_currency`;
произвольная crypto-to-crypto пара с двумя instrument UUID потребует отдельного
расширения публичного operation contract.

Последствия: повторный пересчёт одинакового набора operations и prices даёт те же
финансовые значения. FIFO, валютная консолидация в base currency и исторические
версии snapshot не входят в этот этап и могут быть добавлены как отдельные policy
и модели без изменения чистой границы ядра.

## ADR-019: Отложенный перенос расчётного ядра в C++

**Статус:** принято.

На момент решения вход и выход Python-ядра были зафиксированы как контракт версии
1; ADR-027 повысил его до версии 2 после добавления двухактивной CEX-сделки.
Эталонной реализацией
остаётся `calculate_positions`; типы, инварианты, порядок результатов, Decimal-
семантика и стабильные коды diagnostics описаны в `docs/CALCULATION_CORE.md`.

Детерминированный benchmark моделирует 8 счетов, 250 инструментов, две валюты и
смесь торговых, комиссионных, налоговых, доходных, денежных и конверсионных
операций. На Python 3.13.13/macOS arm64 семь последовательных прогонов после
прогрева дали медиану 0,047 секунды для 10 тысяч, 0,166 секунды для 50 тысяч и
0,316 секунды для 100 тысяч операций. Максимум для 100 тысяч составил 0,366
секунды. Генерация входа, загрузка из БД и сохранение snapshot не измерялись.

Решение: не создавать pybind11-модуль в первой фазе. Для ручного локального
пересчёта чистое Python-ядро не показало измеримого ограничения, а C++ потребовал
бы отдельной реализации точной десятичной арифметики и постоянной проверки полной
семантической эквивалентности. Перенос до появления новых operation shapes также
закрепил бы межъязыковую границу преждевременно.

Решение пересматривается после следующих импортных форматов или раньше, если
профилирование полного API-пересчёта на целевой среде покажет, что именно ядро, а
не чтение или запись PostgreSQL, существенно влияет на целевую задержку. Тогда
Python остаётся эталоном, а C++ обязан совпасть с ним на полном результате без
`float` или `double` для финансовых значений.

Последствия: архитектурная возможность из ADR-002 сохраняется, но C++ больше не
является обязательной работой первой фазы. В проекте остаётся воспроизводимая
контрольная точка для будущего сравнения.

## ADR-020: Scope ограничен брокерскими счетами и CEX

**Статус:** принято.

После оценки чувствительности и практической ценности банковских данных решено не
импортировать обычные банковские счета, карты, вклады и историю покупок. Продукт
фокусируется на брокерских счетах и CEX; кошельки и DeFi остаются более поздними
направлениями.

Существующий enum/type `bank`, созданный в Phase 01, временно сохраняется ради
обратной совместимости миграций и API. Его наличие не означает, что нужно создавать
Universal bank CSV, банковские adapters или банковскую аналитику. Удаление либо
deprecation этого типа является отдельным будущим решением и не блокирует Phase 02.

Последствия: `PRODUCT_SPEC`, `IMPORT_DESIGN`, `PHASE_02` и инструкции агенту должны
использовать один scope. Персональные банковские транзакции не запрашиваются, не
хранятся и не попадают в fixtures.

## ADR-021: Первые реальные adapters — Т‑Инвестиции XLSX и Альфа XML import

**Статус:** принято.

Первыми provider-specific форматами выбраны официальный брокерский XLSX
Т‑Инвестиций и XML Альфа‑Инвестиций с корнем `report_broker`, предназначенный для
импорта. XLSX Альфы используется только для человеческой сверки и не является
основным машинным контрактом версии 1.

Каждый provider получает отдельный versioned adapter. Пользователь явно выбирает
provider, но adapter обязан самостоятельно подтвердить внутреннюю структуру файла.
Оригинальные пользовательские отчёты остаются вне project tree; в репозитории
разрешены только полностью искусственные structural fixtures.

Для Альфы источником ledger operations являются прежде всего завершённые сделки и
несвязанные денежные события. `money_moves` с `trd_no` являются денежной стороной,
НКД или комиссией уже известной сделки и не импортируются повторно. Незавершённые
сделки не подтверждаются. Позиции и report totals используются для reconciliation.
Переносы бумаг остаются на review до явной политики себестоимости.

Для Т‑Инвестиций исполненные сделки создают trade и отдельные fee candidates;
справочник инструментов, денежные остатки и движение ценных бумаг используются для
сопоставления и reconciliation. Пустые секции допустимы.

Последствия: Phase 02 сначала реализует безопасный XML upload и оба брокерских
adapter, затем решает overlap/completeness, и только после этого переходит к CEX.

## ADR-022: Потоковая защита XML на upload и worker boundaries

**Статус:** принято.

XML считается недоверенным вводом дважды. Upload до записи в постоянное storage
проверяет extension, allowlist content type, сигнатуру после BOM/whitespace и весь
документ потоковым Python Expat parser. DTD, объявления entity, skipped/unparsed
entity, notation и external entity callback запрещены; parameter entity parsing
отключён, сетевой resolver отсутствует. После сверки сохранённого size и SHA-256
worker повторяет ту же security validation до provider detection и staging.

Resource policy первой версии: общий file limit 25 MiB, XML depth 64, 100 000
элементов, 65 536 символов в text/attribute/comment/processing-instruction value и
не более 128 attributes на элемент. Первые три XML-лимита настраиваются через
`FINANCE_IMPORT_XML_*`; изменение default требует риск-ориентированной проверки.
HTML root не считается XML import document и отклоняется на общей границе upload.

Parser exception, line contents и значения документа не возвращаются и не
логируются. Диагностика содержит только стабильный code и обобщённое сообщение.
Проверка выполняется до постоянного storage, но сама запись остаётся chunked и
сохраняет существующие server-generated key, SHA-256 и duplicate-upload гарантии.

Последствия: отдельная зависимость XML parser пока не нужна; безопасность не
опирается на добросовестность будущего Alfa adapter. Provider adapter всё равно
обязан независимо проверить root и обязательные коллекции. Полное чтение XML
выполняется дважды (upload и worker), что является осознанной ценой defense in
depth для ручных файлов, ограниченных 25 MiB.

## ADR-023: T-Investments XLSX v1 и reconciliation-only staging

**Статус:** принято.

Официальный XLSX Т‑Инвестиций обрабатывается отдельным adapter
`tbank_broker_xlsx` версии `1.0`; universal CSV parser не содержит provider
branches. Adapter использует openpyxl в read-only/data-only режиме, предварительно
ограничивает ZIP числом 2 048 entries и 100 MiB суммарного uncompressed content,
затем ограничивает sheet 100 000 строками и 512 колонками. Detection требует лист
`broker_rep`, документированный заголовок периода, основные sections и trade
columns. Изменение этих markers требует проверки совместимости версии.

Trade date/time без offset получает `Europe/Moscow`. Все числовые значения сразу
преобразуются в Decimal contracts; вычисления на float не выполняются. Номер сделки
является external ID trade. Комиссионные компоненты агрегируются по валюте, а fee
получает derived external ID `<trade>:fee:<currency>`: это сохраняет связь с
исходной сделкой и не создаёт коллизию между trade и fee либо комиссиями в разных
валютах. Instrument matching использует валидный ISIN первым, затем
provider+provider code; неизвестный инструмент не создаётся.

Денежные остатки и движение ценных бумаг сохраняются как excluded staging rows с
raw traceability и стабильной reconciliation diagnostic. У них нет normalized
operation candidate, поэтому confirm их пропускает и не создаёт вымышленные сделки
или cash movements. Для корректной SQL-семантики `normalized_candidate=None`
хранится как SQL NULL, а не JSON null.

Последствия: reconciliation values доступны для будущих проверок раздела 5, но
сейчас не влияют на ledger. Synthetic fixture подтверждает структуру, а не полную
provider specification; новые обезличенные варианты официального отчёта должны
проходить отдельную regression validation до признания совместимыми с `1.0`.

## ADR-024: Alfa XML v1, trade-linked money и transfer review

**Статус:** принято.

XML Альфа‑Инвестиций обрабатывается отдельным adapter
`alfa_broker_xml_import` версии `1.0`. Перед `ElementTree` adapter повторно вызывает
общую потоковую XML security validation из ADR-022; поэтому дерево строится только
после ограничений размера, глубины, количества элементов и длины значений и после
запрета DTD/entities. Detection требует root `report_broker`, metadata, коллекции
`positions`, `trades_finished`, `trades_unfinished`, `money_moves`, `transfers` и
валидный период. `money_moves_total` остаётся необязательной reconciliation-секцией
с явной diagnostic при отсутствии.

Завершённая сделка создаёт trade по знаку точного `qty`; знак `summ_trade` не
участвует в направлении. Ненулевой `bank_tax` создаёт отдельный fee. Trade и fee
сохраняют один исходный `trade_no`: fingerprint уже включает operation type и
разделяет их без искусственного изменения provider ID. Для операций из XML добавлен
ledger source type `xml_import` и CHECK-миграция `0009_xml_operation_source`.

Instrument matching использует валидный `isin_reg`, затем provider code из
сопоставленной позиции: `p_code`, а при его отсутствии `act_id`. Это сохраняет
приоритет глобального ISIN, поддерживает observed Alfa fields и не создаёт
инструменты молча. Naive datetime получает `Europe/Moscow`; точность выбирается по
фактически присутствующим долям секунды.

Любой непустой `money_moves.trd_no` обязан ссылаться на завершённую сделку, иначе
строка становится ошибкой и блокирует confirm. Найденные settlement, НКД и
комиссия сохраняются как excluded reconciliation rows и не создают второй cash
movement, income или fee. Несвязанные client deposit/withdrawal, coupon/dividend и
bank tariff нормализуются по устойчивым группам; неизвестная группа требует review.
Позиции, totals и незавершённые сделки excluded и не влияют на ledger.

Transfer бумаги отличается от reconciliation: он сохраняется warning-строкой и
блокирует confirm, пока пользователь явно не исключит его. Автоматически превращать
transfer в trade или adjustment запрещено до отдельной политики переноса
себестоимости. Последствия: полный импорт остаётся безопасным и трассируемым, а
раздел 5 может добавить reconciliation/completeness без изменения правил уже
созданных операций.

## ADR-025: Period-delta reconciliation без скрытых корректировок

**Статус:** принято.

Полнота import batch использует четыре явных значения: `full_ledger` для полной
истории счёта, `period_ledger` для операций ограниченного отчётного периода,
`snapshot_with_movements` для снимка с движениями и `unknown`, когда источник не
даёт достаточной гарантии. Provider-specific отчёты Т‑Инвестиций и Альфы версии
1.0 классифицируются как `period_ledger`; Universal broker CSV остаётся `unknown`.
Миграция `0010_import_reconciliation` отображает прежние значения без потери
смысла и добавляет status/summary batch и машинные control data staging rows.

Reconciliation сравнивает не абсолютный текущий Ledger, а точные дельты самого
отчёта: `closing - opening` отдельно по валюте и идентификатору инструмента.
Расчётные эффекты берутся из всех экономических строк отчёта, включая найденные
дубли overlap batch, потому что контрольные итоги источника также включают эти
строки. В Ledger при confirm по-прежнему попадают только рассмотренные новые
операции. Денежный эффект trade считается как `quantity * price` с направлением,
а fee/tax, income, cash movement и exchange учитываются отдельными точными
Decimal-ногами.

Итог имеет `not_available`, `matched` или `mismatch`. Несовпадение сохраняется как
безопасная diagnostic с видом и количеством проверок, без instrument keys, сумм и
raw XML/XLSX values. Оно не создаёт `balance_adjustment` и не блокирует confirm:
официальный отчёт может содержать ещё не нормализованные события. Повреждённая или
структурно неверная reconciliation metadata, напротив, возвращает
`import_reconciliation_invalid` до создания первой Ledger operation; confirm
остаётся атомарным.

Ненулевой opening position означает, что историческая себестоимость до начала
отчёта неизвестна. Это фиксируется `import_initial_state_not_imported`; система не
подменяет basis нулём и не создаёт начальную покупку. Входящий transfer Альфы с
неизвестной себестоимостью сохраняет принятую в ADR-024 review policy: строка
должна быть явно исключена, не становится trade/adjustment и не создаёт ложный
realised P&L. Канонический `instrument_transfer` остаётся будущим решением только
для источника, который передаёт достаточную информацию о переносимой basis.

Последствия: overlap можно проверять независимо от уже подтверждённой истории,
видимое mismatch не искажает финансовые данные, а публичный preview показывает
период, полноту, operation/diagnostic counts и безопасный reconciliation status.

## ADR-026: Bybit Spot как первый CEX и связанный CSV bundle

**Статус:** принято.

Первый CEX source — ручной официальный export Bybit Spot. Логический формат
`bybit_spot_csv_bundle` версии `1.0` состоит из Spot Trade History, UTA Asset
Change Details, Funding Asset Change Details и withdraw/deposit history. Все
наблюдаемые timestamps являются UTC. Исходные пользовательские файлы не входят в
project tree; `docs/fixtures/bybit_*_synthetic_v1.csv` воспроизводят только headers,
форму строк и межфайловые связи в новом искусственном экономическом сценарии.

Bundle является одной импортной единицей, но каждый документ должен иметь свой
storage object, размер, SHA-256 и traceability. Пользователь выбирает несколько
CSV в одном upload; требовать ручной ZIP нельзя. Metadata UID обязан совпадать во
всех документах и используется только для detection/consistency, не становится
публичным account identifier и не попадает в diagnostics.

Spot Trade History является authoritative источником execution, transaction ID и
order ID, но не содержит fee asset. Две UTA `TRADE` строки с тем же contract,
direction и UTC timestamp выражают отданную и полученную asset-ноги; отрицательный
`Fee Paid` указывает фактический fee asset. Adapter не выводит fee asset из
направления сделки. Missing или неоднозначная связь блокирует частичное создание
trade и требует review.

UTA/Funding internal transfer и Funding/on-chain withdrawal являются разными
представлениями одного движения и дедуплицируются внутри bundle. Внутренний transfer
не меняет совокупный капитал CEX account; deposit/withdrawal выражаются asset
transfer и не создают realised P&L. Наблюдавшиеся Airdrop, Fiat/P2P и IPO остаются
на review до отдельной политики. Fee в третьем asset и deposit в переданной
выборке не наблюдались: каноническая модель обязана их допускать, но provider
adapter не имитирует неподтверждённую строку.

Последствия: текущая one-file import модель должна получить обратно совместимый
multi-document batch; crypto trade contract — две instrument legs и отдельная
instrument fee, а не четырёхсимвольная `price_currency`. Python calculation core
остаётся эталоном и должен совпасть на новых CEX контрольных сценариях.

## ADR-027: Multi-document staging и двухактивный Ledger contract

**Статус:** принято.

Multi-document batch реализуется дочерней таблицей `import_batch_files`: каждый
CSV имеет server-generated storage key, исходное безопасное имя, размер, SHA-256,
порядковый номер и detected document type. `import_rows.source_file_id` связывает
staging с конкретным документом. Прежние поля основного файла в `import_batches`
сохраняются для обратной совместимости; миграция создаёт для старого batch одну
дочернюю запись. Для одного файла batch SHA остаётся прежним file SHA, для bundle
он вычисляется из сортированного набора document SHA с versioned domain separator,
поэтому duplicate upload не зависит от порядка выбора файлов.

Публичный Ledger получает `crypto_trade` с
`sold_instrument_id/sold_quantity` и
`bought_instrument_id/bought_quantity`. Колонка `instrument_id` остаётся primary
reference и содержит bought asset, новая `secondary_instrument_id` — sold asset;
фильтр операций ищет по обеим. Старый `trade` не меняется. Тип `fee` принимает две
непересекающиеся формы: прежнюю денежную `amount/currency` и asset fee
`instrument_id/quantity`. Это поддерживает комиссии в base, quote и третьем asset
без изменения торгового notional и без двоичной арифметики.

Calculation contract повышен до версии 2. Crypto trade переносит известную
weighted-average basis проданной доли в полученный asset и не фиксирует realised
P&L без денежной оценки. При неизвестной basis количество сохраняется, а basis
остаётся неизвестной с diagnostic. Asset fee списывает количество и
пропорциональную basis без cash effect и realised P&L; денежные fee сохраняют
прежние currency metrics. Deposit/withdrawal используют `crypto_transfer` и также
не создают realised P&L.

Bybit adapter требует ровно четыре типа документов и единый UID, но удаляет UID
из staging raw data и не включает значения в diagnostics. Spot execution должна
иметь ровно две UTA trade legs; internal UTA/Funding transfer исключается только
при точном совпадении asset, UTC time, направления и суммы. Funding/on-chain
withdrawal создаёт один transfer и при разнице сумм одну asset network fee.
Неполная или неоднозначная связь, Airdrop, Fiat/P2P и IPO остаются review-only.

Последствия: миграция `0011_bybit_spot_bundle` обязательна до запуска нового кода.
Однофайловые adapters и публичные diagnostics сохраняют прежнюю форму. Возможная
будущая C++-реализация должна реализовать contract v2; Python остаётся эталоном.

## ADR-028: Allocation как следующий приоритет после Phase 02

**Статус:** исторически принято; часть про target weights superseded ADR-044.

Phase 02 завершила два provider-specific брокерских адаптера и первый CEX adapter.
Расширять число источников до появления новой подтверждённой структурной выборки
менее ценно, чем реализовать уже заявленную в Product Spec работу с категориями и
целевыми весами. Поэтому следующий приоритет — backend-allocation, а не второй CEX.

Allocation должна использовать рассчитанные snapshots и точные `Decimal`/`NUMERIC`
значения. Первый исполняемый план должен определить таксономию категорий, область
действия target weights, правила валидации суммы весов и API сравнения фактической
и целевой структуры. Неизвестная цена или себестоимость обязана оставаться явной
diagnostic; система не должна достраивать оценку скрытыми значениями.

Последствия: исполняемый план находится в `docs/PHASE_03.md`; первый шаг —
зафиксировать методики актуальной оценки и неполных данных. Frontend, инвестиционные
рекомендации, ребалансирующие сделки, реальные provider API и банковские продукты
остаются вне scope.

## ADR-029: Phase 03 строит current analytics без instrument-price time series

**Статус:** принято; часть про target allocation superseded ADR-044.

После завершения трёх ручных provider imports следующий пользовательский результат
— не новый источник и не деплой, а агрегированная аналитика поверх подтверждённого
Ledger. Phase 03 реализует текущую оценку, категории, target allocation,
breakdowns, counterparty exposure, временные ряды событий Ledger и единый
data-quality contract. Ответы предназначены для Swagger сейчас и будущего frontend,
который не должен повторять финансовые расчёты.

Источниками остаются ручные операции, импортированные файлы и ручные price
observations. Приватные provider API, автоматические цены инструментов,
исторические котировки инструментов и daily portfolio value не входят в фазу.
ADR-031 отдельно разрешает системный публичный FX gateway. Timeline показывает
только достоверные события Ledger — cash flows, income, fees, taxes, turnover и
доступный realised P&L. Конвертировать прошлое сегодняшним курсом запрещено.

Текущая консолидация в base currency использует последнюю price/FX observation с
`observed_at <= valuation_as_of`. Компонент без цены или курса не получает скрытое
значение: полный `total_value` недоступен, а API возвращает `known_value`, coverage
и стабильную diagnostic. Allocation рассчитывается по явно указанному denominator
и не превращается в ребалансирующие сделки или инвестиционную рекомендацию.

Последствия: Phase 03 требует FX domain, allocation models и отдельную analytics
application boundary. FX scheduler остаётся Python I/O-компонентом и не требует
C++. Метрики TWR,
XIRR, Sharpe, Sortino, volatility, drawdown и график рыночной стоимости откладываются
до отдельного решения о Market Data. Исполняемый порядок зафиксирован в
`docs/PHASE_03.md`.

## ADR-030: Актуальная аналитика выбирает RUB или USD

**Статус:** принято.

Пользователь выбирает `reporting_currency=RUB|USD` для актуальных overview,
holdings, breakdown, exposure и allocation. `portfolio.base_currency` остаётся
валютой по умолчанию, но не ограничивает вывод. Переключение reporting currency
не меняет Ledger, cost basis или calculation snapshot: analytics application
повторно агрегирует один актуальный результат с подходящими ручными price/FX
observations на `valuation_as_of`.

Цены инструментов остаются ручными. Fiat FX rates получает разрешённый в ADR-031
публичный gateway, а пользователь или оператор может сохранить курс вручную через
Swagger как fallback. Если нужного курса к RUB/USD нет, API возвращает partial
`known_value` и diagnostic, а не считает курс равным единице. USDT и USD также не
считаются эквивалентными без явной price/FX observation.

Выбор RUB/USD относится только к актуальной оценке. Исторические Ledger events
возвращаются раздельно в исходных currencies/assets, потому что conversion каждого
bucket требует курса на дату события. Применять сегодняшний USD/RUB к прошлому
запрещено. Единый исторический график в RUB/USD появится только после отдельного
решения об исторических FX/market data.

## ADR-031: Публичный FX gateway разрешён в Phase 03

**Статус:** принято; уточняет ADR-029 и ADR-030.

Запрет API в ближайших фазах относится к импорту пользовательских данных из
брокеров и CEX. Системный read-only gateway публичных fiat FX rates разрешён,
потому что не получает сведения о портфелях, не использует пользовательские
credentials и обслуживает одинаковые курсы для всех локальных портфелей.

Analytics endpoint не обращается к внешней сети. Отдельный Python worker получает
FX по расписанию через интерфейс `FxRateProvider`, валидирует точный rate и время,
идемпотентно сохраняет append-only observation в PostgreSQL. Timeout, retry,
backoff, rate limit и stale policy обязательны. При отказе источника последнее
валидное значение сохраняется, а ручной Swagger input остаётся fallback.

Первая обязательная пара — USD/RUB, поскольку публичная аналитика выбирает RUB или
USD. Для других fiat currencies допустим direct, inverse или один явно
документированный pivot через RUB/USD; произвольный FX graph search запрещён.
Источник и семантика курса — официальный дневной или рыночный — выбираются и
фиксируются до реализации adapter.

Worker накапливает датированные FX observations, но текущий курс не применяется к
прошлым событиям. Исторический bucket конвертируется только при полном покрытии
его событий курсами соответствующих дат. Автоматические цены инструментов,
исторические котировки акций/облигаций/криптоактивов и private provider APIs всё
ещё не входят в Phase 03.

C++ не используется: gateway ограничен HTTP I/O и небольшими точными Decimal
преобразованиями. Python calculation engine остаётся эталоном; вопрос C++
пересматривается только по результату профилирования CPU-bound аналитики.

## ADR-032: Методика current valuation и явная неполнота

**Статус:** принято.

Любая актуальная оценка имеет `valuation_as_of`. Цена или FX observation подходит
только при `observed_at <= valuation_as_of`; будущее значение не используется даже
если оно уже сохранено. Публичные current analytics принимают
`reporting_currency=RUB|USD`, по умолчанию используют `portfolio.base_currency` и
всегда возвращают фактически выбранную валюту.

Метрики независимы и не смешиваются:

- current value — сумма market value оценённых позиций и денежных остатков;
- cost basis — сумма только известной basis открытых позиций;
- realised и unrealised P&L — signed торговые результаты;
- income, fees и taxes — отдельные положительные величины своих типов;
- deposits и withdrawals — отдельные положительные внешние потоки, а net external
  flow равен `deposits - withdrawals`;
- total result, когда все его компоненты доступны, равен
  `realised + unrealised + income - fees - taxes`; cash flow в него не входит.

Разновалютная компонента сначала умножается на явно разрешённый FX rate и
округляется `ROUND_HALF_EVEN` до Money scale 18, затем входит в сумму. Для
одинаковой валюты rate не нужен; для разных валют отсутствие курса никогда не
заменяется единицей. Неизвестная basis, цена или FX блокирует только зависимую
компоненту/метрику.

Quality имеет три значения: `complete`, если все компоненты учтены; `partial`,
если есть и известные, и исключённые компоненты; `unavailable`, если ни одной
зависимой компоненты вычислить нельзя. `total_value` существует только для
`complete`; `known_value` и included/excluded counts остаются видимыми всегда.
Совместимая форма planned analytics response:

```json
{
  "metric": "current_value",
  "valuation_as_of": "2026-08-22T00:00:00Z",
  "reporting_currency": "USD",
  "quality": "partial",
  "total_value": null,
  "known_value": "1250.000000000000000000",
  "included_components": 2,
  "excluded_components": 1,
  "diagnostics": [
    {
      "severity": "warning",
      "code": "fx_rate_missing",
      "message": "A required exchange rate is unavailable"
    }
  ]
}
```

Последствия: frontend не должен суммировать валюты или достраивать missing values.
Стабильный contract реализован в `analytics.contracts`; конкретные overview и
holdings endpoints используют его в разделе 5 Phase 03.

## ADR-033: Официальный дневной CBR FX и ручной fallback

**Статус:** принято.

Primary FX provider версии 1 — публичный XML Банка России
`https://www.cbr.ru/scripts/XML_daily.asp`. Это официальный дневной курс валют к
RUB, а не intraday market quote и не обязательство купить или продать валюту по
этому значению. Для `USD/RUB` rate означает количество RUB за одну USD. Корневую
дату действия provider публикует без времени; система задаёт ей 00:00
`Europe/Moscow` и сохраняет UTC instant. `fetched_at` отдельно фиксирует время
получения.

`exchange_rates` является append-only и хранит точный `NUMERIC(38,24)`, пару,
`observed_at`, `fetched_at`, provider/source и mode `automatic|manual`. Automatic
observation идемпотентно по provider+pair+observed_at и не перезаписывается даже
если повторный ответ отличается. Manual batch использует отдельный provider scope
и одну транзакцию. `market_prices` остаются только ручными и также append-only.

FastAPI не обращается во внешнюю сеть. `POST /api/v1/fx-rates/sync` ставит
rate-limited `fx_sync` в существующую PostgreSQL queue; отдельная ветка Python
worker вызывает `FxRateProvider`. Payload содержит только системную пару USD/RUB:
worker не читает portfolio, accounts, Ledger, import raw rows или credentials.
Default policy: timeout 5 секунд, до трёх попыток с exponential backoff, response
не более 512 KiB, безопасный bounded XML parse без DTD/entities и минимум 60 секунд
между enqueue. Ошибка сохраняет только стабильный code/message и не удаляет
последнее валидное observation.

Resolution выбирает direct, затем inverse, затем максимум один pivot через RUB;
произвольный graph search запрещён. Rate старше 72 часов остаётся доступным, но
получает `stale` diagnostic и точный age. Missing rate даёт `unavailable`, не
единицу. Ручные `/prices/batch` и `/fx-rates/batch` являются fallback; один
невалидный элемент откатывает весь batch. Автоматические цены инструментов всё ещё
вне Phase 03.

Последствия: миграция `0012_phase03_pricing_fx` расширяет очередь nullable scope и
при downgrade удаляет только FX jobs/rates новой фазы. Semantics provider основана
на официальной документации Банка России:
`https://www.cbr.ru/development/sxml/`.

## ADR-034: Системные allocation classes и portfolio overrides

**Статус:** принято; consequence про allocation targets superseded ADR-044.

Allocation использует семь глобальных неизменяемых категорий с устойчивыми UUID:
`equity`, `fixed_income`, `fund`, `derivative`, `crypto`, `cash`, `other`.
Неразмеченный инструмент получает системную категорию детерминированно из
`instrument_type`; денежный остаток относится к `cash` напрямую и не требует
создания инструмента. `currency` instrument также по умолчанию относится к cash.

Пользовательская категория принадлежит ровно одному portfolio и обязательно
указывает родительский system class. Override хранится по уникальной паре
portfolio+instrument, ссылается только на глобальную system category либо custom
category того же portfolio, а глобальный instrument не изменяет. Проверка области
видимости выполняется application service; foreign keys защищают удаление
используемой категории, а system categories запрещено изменять через API.

Последствия: allocation targets могут одинаково ссылаться на system и custom
categories через один UUID. Sector/country/issuer taxonomy не добавляется без
подтверждённых справочников. Миграция `0013_allocation_categories` создаёт и
засевает системные записи, а downgrade удаляет только allocation metadata.

## ADR-035: Atomic target plan и exact actual weights

**Статус:** superseded решением ADR-044. Ниже сохранён исторический контракт,
реализованный в Phase 03.

Portfolio имеет не более одного активного target plan. Его полный набор
заменяется `PUT` одной транзакцией; category IDs проверяются до удаления прежних
строк, веса принимаются только как exact Decimal strings в диапазоне `0..1`, а
сумма должна быть ровно `1` без неявной normalization. Хранение использует
`NUMERIC(38,24)`. System cash и portfolio custom categories равноправны.

Actual weight рассчитывается только по current holdings, которые удалось оценить
в выбранной reporting currency. Ответ явно содержит known denominator,
included/excluded counts и quality. Missing holding не получает нулевую стоимость;
при неположительном denominator weights недоступны. Каждая доля округляется
`ROUND_HALF_EVEN` до 24 знаков, затем единственный decimal residual добавляется
к крупнейшей известной категории с устойчивым UUID tie-break. Поэтому сумма
опубликованных actual weights ровно `1`, а пропуски всё равно видимы как partial.

Target, actual и signed deviation являются описанием структуры, а не расчётом
сделок или рекомендацией. Отложенные foreign keys category references позволяют
атомарно удалить весь portfolio, но прямое удаление используемой custom category
по-прежнему завершается conflict на commit. Миграция — `0014_allocation_targets`.

## ADR-036: Current analytics как несохраняемый read model snapshot

**Статус:** принято.

Overview, holdings, breakdown, counterparty exposure и allocation comparison не
хранят собственные агрегаты. `analytics.service` читает calculation snapshot,
текущий Ledger count, pricing/FX, allocation и справочные metadata только через
application services и строит response schemas на запрос. В Phase 03 учитываются
только broker и CEX accounts; legacy `bank` type не расширяет продуктовый scope.

`valuation_as_of` current read model равен времени calculation snapshot. Snapshot
считается fresh, только если его `operation_count` равен числу операций текущего
Ledger. При расхождении API сохраняет известные snapshot values для объяснимости,
но добавляет неизвестную компоненту: quality становится partial/unavailable,
`total_value` скрывается и возвращается `calculation_snapshot_stale`. Portfolio
без Ledger и snapshot является корректным пустым состоянием с нулевым overview.

Reporting currency выбирается из RUB/USD; base currency используется по умолчанию,
если она поддерживается. Для legacy portfolio с другой base currency без явного
query применяется RUB и возвращается `reporting_currency_defaulted`. Все пять
breakdown dimensions используют тот же known-value denominator, что overview.
Counterparty exposure группирует только стоимость по broker/CEX institution и не
даёт оценку риска. Stale price/FX остаются используемыми только с diagnostic,
missing price/FX/basis не подменяются нулём или единицей.

## ADR-037: Ledger timelines используют отдельный operation-effects contract

**Статус:** принято.

Историческая аналитика Phase 03 является временным рядом событий Ledger, а не
рядом цены инструмента или ежедневной стоимости портфеля. Endpoint'ы принимают
inclusive local `from`, exclusive local `to`, `day|week|month` и каноническое имя
IANA timezone. Локальные календарные границы переводятся в aware UTC instants;
операции продолжают храниться и сравниваться как timezone-aware datetime.

Для realised P&L и basis введён чистый `operation-effects` contract версии 1.
Он детерминированно повторяет операции в порядке `occurred_at, operation_id` теми
же weighted-average правилами calculation contract v2 и возвращает per-operation
изменения quantity/cost basis, realised P&L либо явную недоступность и безопасные
diagnostics. История до `from` участвует в replay, поэтому продажа внутри периода
получает корректную basis; в series попадают только события выбранного интервала.
Эффекты и buckets не сохраняются отдельными таблицами: Ledger остаётся источником
истины, а response provenance содержит версии обоих контрактов, calculation cutoff,
snapshot as-of и freshness.

Денежные события возвращаются по исходной currency, crypto turnover и asset fee —
по UUID asset unit. Fee и tax остаются независимыми series и не дублируются в
скрытом total result. Crypto transfer не является turnover или realised P&L.
Исторические endpoint'ы не принимают `reporting_currency` и всегда возвращают
`historical_reporting_conversion=unavailable`: накопленные FX observations пока
не используются, поэтому невозможно частично конвертировать bucket или применить
к прошлому текущий курс. Полная датированная конвертация всех событий bucket может
быть добавлена только новым совместимым контрактом.

Последствия: четыре read-only endpoint'а (`cash-flows`, `income`, `costs`,
`trading`) не требуют миграции БД и естественно наследуют Ledger/import
deduplication. Ограничение диапазона и pagination остаются задачей раздела 8.

## ADR-038: Data quality является безопасной проекцией существующих contracts

**Статус:** принято.

`GET .../analytics/data-quality` не вводит отдельный рейтинг качества и не хранит
дублирующую таблицу diagnostics. Analytics переиспользует текущий read model, а
imports предоставляет только portfolio-level counts: period-limited/unknown
completeness, reconciliation mismatch и unresolved review. Calculation diagnostics,
missing/stale price/FX и unknown basis агрегируются в стабильные
`code/severity/count` с безопасными фиксированными сообщениями.

Public diagnostic не содержит batch/account/instrument IDs, provider UID,
addresses, raw staging, report controls или финансовые значения. `count` означает
число затронутых безопасных source diagnostics/batches/rows, а не сумму или размер
позиции. Каждый code возвращает явные endpoint/metric impacts с фактическим
`complete|partial|unavailable`; независимая метрика сохраняет собственное состояние
и не наследует худший статус всего портфеля. В частности missing market price может
делать current value partial, оставляя известную cost basis complete.

Provenance содержит calculation contract version, snapshot as-of/freshness и
времена реально использованных market price/FX observations. Observation IDs,
instrument mapping, rate и price не публикуются. Повторно использованное одним или
несколькими holdings observation учитывается один раз по внутреннему ID, даже если
несколько observations имеют одинаковое время.

Неизвестная basis теперь добавляет отсутствующую компоненту realised P&L в current
metric aggregation, не суммируя position realised P&L второй раз с currency
metrics. Это блокирует только зависимый realised metric и сохраняет income, fees,
taxes и доступную current value независимыми.

Последствия: data-quality contract добавлен без миграции БД и без раскрытия ORM.
Новые диагностические источники должны сначала предоставить безопасный application
summary и явную карту impacts; передача raw JSON из import/calculation storage в
этот endpoint запрещена.

## ADR-039: Frontend-facing analytics contract ограничен и детерминирован

**Статус:** принято.

Все analytics и allocation endpoint'ы возвращают отдельные Pydantic response
schemas; ORM-модели не являются публичным API. Breakdown items сохраняют
устойчивые keys, а каждая timeline series получает детерминированный
`<metric>:<unit_type>:<unit>`. Коллекции всегда являются массивами, в том числе в
пустом portfolio или после filter; JSON `null` используется только для
недоступной метрики, но не вместо пустой коллекции.

Event timeline применяет inclusive local `from`, exclusive local `to`, canonical
IANA timezone и максимум 366 календарных дней. Optional `unit_type` и `unit`
являются exact filters. Series сортируются по metric, unit type и unit, buckets —
по возрастанию; `limit` 1..100 и `offset` применяются только к series, а response
возвращает `series_total`, applied limit и offset. Так один series остаётся
семантически целым, а replay Ledger имеет bounded верхнюю границу.

OpenAPI содержит synthetic complete, partial и empty overview examples. Partial
example явно сохраняет required `total_value: null`; examples добавляются в
сгенерированный OpenAPI cache после стандартной FastAPI generation, потому что её
metadata encoder иначе удаляет `None`. Runtime response validation остаётся
обычной Pydantic/FastAPI границей.

Последствия: будущий frontend использует stable keys и public metadata, не
пересчитывает финансовые метрики и не выводит порядок массива из presentation
labels. Cursor pagination и server-side daily portfolio value не добавляются без
нового контракта.

## ADR-040: Следующая фаза — локальный frontend v1

**Статус:** исторически принято по прямому решению пользователя; перечисление
allocation targets superseded ADR-044.

После завершения Phase 03 следующим приоритетом выбрана первая локальная web
frontend-версия, а не отдельная Market Data phase. Она потребляет только стабильный
`/api/v1`: import upload/preview/review/confirm, ручные prices/FX, current
analytics, holdings/breakdown/exposure, allocation targets, Ledger event timelines
и data quality. Backend остаётся единственным владельцем финансовых формул,
Decimal normalization, quality states и diagnostics.

Frontend не получает прямой доступ к PostgreSQL, ObjectStorage, worker или ORM и
не достраивает missing values, historical FX либо инвестиционные рекомендации.
Phase 04 остаётся local single-user: authentication, production deployment,
private broker/CEX APIs, mobile и trading не добавляются. Toolchain и exact UI
scope фиксируются первым разделом исполняемого плана до scaffold, без изменения
публичной Ledger модели.

Последствия: Market Data сохраняется будущим отдельным решением. Следующий
исполняемый пункт — `PHASE_04.md`, раздел 1 «Зафиксировать frontend v1 contract и
toolchain».

## ADR-041: Refined frontend v1 является утверждённым визуальным контрактом

**Статус:** принято по прямому решению пользователя 22.08.2026.

Для Phase 04 утверждён единый refined design direction и восемь reference images
из `docs/design-concepts/frontend-v1/`: семь desktop screens для overview,
holdings, import start/review, data quality, allocation и Ledger events, а также
tablet recomposition overview. Они заменяют ранние альтернативные концепты как
источник визуального направления, но не изменяют PRODUCT_SPEC или public API.

`DESIGN_DIRECTION_FRONTEND_V1.md` определяет visual system и composition rules,
`OPENAPI_UI_CHECK.md` связывает экраны с `/api/v1`, а `design-data.json` является
только synthetic visual fixture. Runtime frontend обязан получать данные через
generated OpenAPI client; демонстрационные значения, labels или derived metrics
из mockup нельзя hardcode как domain contract. При расхождении макета и OpenAPI
приоритет имеют financial semantics backend, Decimal/null/empty contract и
безопасность данных. Существенное визуальное отклонение документируется.

Последствия: в Phase 04 больше не требуется выбирать новую концепцию. Реализация
начинается с toolchain, API client и design tokens, затем идёт по утверждённым
экранам. Готовность включает screenshot comparison для семи desktop screens и
tablet overview, но не требует pixel-perfect подмены доступности или корректности.

## ADR-042: Frontend v1 использует generated OpenAPI client и отдельную workspace boundary

**Статус:** принято и реализовано 22.08.2026.

Frontend размещён в `frontend/` с зафиксированными Node 22.17.1, npm 10.9.2,
React 19.2.8, Vite 8.2.2 и TypeScript 5.9.3. npm lockfile обязателен. Для трёх
специализированных задач выбрано по одной библиотеке: Base UI 1.7.0 для доступных
primitives, React Virtuoso 4.18.12 для длинных таблиц и Recharts 3.10.1 для
presentation-графиков. TanStack Query владеет server state, React Router —
устойчивыми URLs, `decimal.js` — только exact formatting/form validation.

OpenAPI экспортируется `scripts/export_openapi.py`; `openapi-typescript` генерирует
единственный TypeScript contract, а `openapi-fetch` создаёт typed client.
`npm run api:check` отклоняет drift. Ручные financial response types, browser
агрегация P&L/weights/allocation и подмена backend `null` нулём запрещены.
Графическая библиотека может преобразовать строку в `number` только для координат
уже рассчитанного значения; рядом обязателен exact табличный эквивалент.

Чтобы import flow восстанавливался после reload, public API получил минимальный
`GET /api/v1/imports` с portfolio/account/status filters, limit/offset и сортировкой
от нового к старому. Frontend не читает import tables или ObjectStorage напрямую.
Vite development proxy обслуживает `/api`; production base origin можно задать
явно, но path остаётся `/api/v1`.

Последствия: frontend можно собирать и проверять независимо от Python packages,
но OpenAPI generation требует актуального backend environment. Browser E2E
содержит только два критических synthetic сценария и не вводит coverage target.
Следующий продуктовый приоритет не следует из выбора frontend toolchain и требует
отдельного решения пользователя.

## ADR-043: Единый локальный Compose запускает frontend без nginx

**Статус:** принято по прямому решению пользователя 22.08.2026.

`docker compose up --build` должен запускать PostgreSQL, API, worker и frontend.
Frontend собирается отдельным multi-stage image на закреплённом Node 22.17.1.
Runtime layer не содержит npm dependencies: только production `dist/` и небольшой
Node HTTP server. Он раздаёт hashed assets, поддерживает SPA fallback и проксирует
`/api` и `/health` на Compose DNS target `api:8000`.

nginx, единый внешний порт и production ingress намеренно не добавляются. На host
frontend остаётся на `${FRONTEND_PORT:-5173}`, API — на `${API_PORT:-8000}`.
Frontend зависит от healthy API, имеет собственный healthcheck и запускается от
непривилегированного пользователя `node`.

После обнаруженного 28.08.2026 остановленного import worker локальный Compose
задаёт worker политику `restart: unless-stopped`. API и frontend не считаются
достаточным healthy stack, если отдельный обработчик заданий не запущен. Frontend
перестаёт бесконечно показывать processing для pending parse job старше 30 секунд
и выводит локальную команду восстановления.

Последствия: локальному пользователю достаточно одной Compose-команды, а browser
сохраняет same-origin `/api/v1`. Node static server не заявляется production web
edge: TLS, compression, rate limiting и deployment topology потребуют отдельного
решения. Hot-reload разработка через `npm run dev` остаётся отдельным режимом.

## ADR-044: Target allocation выведен из MVP, actual allocation сохранён

**Статус:** принято по прямому решению пользователя 26.08.2026; supersede'ит
ADR-035 как действующий продуктовый и API-контракт.

Finance Aggregator в MVP собирает подтверждённые данные брокерских счетов и CEX и
показывает фактическое распределение капитала. Управление инвестиционными целями —
отдельная продуктовая задача, которой пользователь не запрашивал. Поэтому actual
allocation и investment goal planning разделены: первая функция остаётся, вторая
не входит в текущий scope.

Сохраняются system/custom allocation categories, default classification,
portfolio-specific instrument overrides, category known values, exact actual
weights, known denominator, included/excluded counts и состояния
`complete|partial|unavailable`. `GET /api/v1/portfolios/{portfolio_id}/allocation`
продолжает возвращать эти backend-calculated значения. Browser использует `number`
только для геометрии диаграммы и не пересчитывает доли.

Удаляются target plan, target weights, signed deviation, frontend editor и
`GET|PUT /api/v1/portfolios/{portfolio_id}/allocation/targets`. Это допустимое
breaking change локального неразвёрнутого API без внешних потребителей.
Forward-миграция `0015_remove_allocation_targets` удаляет таблицы
`allocation_targets` и `allocation_target_plans`; downgrade восстанавливает их
пустую структуру, но не удалённые значения. Применённая миграция
`0014_allocation_targets` сохраняется как исторический факт.

Последствия: `target_weight` и `deviation` отсутствуют в allocation response,
OpenAPI и generated TypeScript contract. Reference image
`06-allocation-desktop.png` используется только по верхнему блоку фактического
распределения; нижний target editor отменён. Возможное возвращение целевых долей
требует нового отдельного решения пользователя и будущей фазы, а не расширения
текущего MVP по умолчанию.

## ADR-045: Официальный ручной импорт является автоматическим happy path

**Статус:** принято по прямому решению пользователя 27.08.2026.

Пользователь загружает без предварительного редактирования официальный отчёт
Т‑Инвестиций, XML «для импорта» Альфа‑Инвестиций либо комплект из четырёх CSV
Bybit. Поддерживаемый provider adapter обязан обработать наблюдаемую официальную
структуру сам. Reconciliation-only строки, внутренние стороны переводов,
агрегатные остатки и незавершённые информационные сделки сохраняются для
трассировки, но не выдаются в frontend как задания пользователю.

Т‑Инвестиции v1 поддерживает исторический `broker_rep` и актуальную много-листовую
XLSX-компоновку. Альфа принимает фактические даты `DD.MM.YYYY H:MM:SS`, учитывает
перенос бумаги как quantity adjustment с неизвестной исторической себестоимостью
и не дублирует связанные денежные расчёты. Bybit различает same-second Spot
executions по точным quantity/value, допускает наблюдаемое расхождение времени
внутреннего transfer до одной секунды и нормализует Airdrop, Fiat/P2P и IPO как
quantity adjustments без выдумывания цены или P&L.

Trusted provider adapters могут пометить instrument reference как пригодный для
автоматического создания. Справочная запись создаётся только при однозначном ISIN,
provider code или crypto asset code и единственном согласованном наборе
name/type/currency. Это не ledger operation. Universal fallback, конфликтующие
metadata, неоднозначный match, возможный дубль и нарушенная связь сделки остаются
на review. Provider также обязан соответствовать типу account: broker reports не
принимаются в CEX account и наоборот.

Frontend показывает обычный итог автоматической обработки и только actionable
warning/error/duplicate rows. Raw staging data и технические исключения не
являются пользовательским workflow. Исходные персональные файлы при анализе
совместимости читаются только на месте и не копируются в репозиторий; synthetic
fixtures остаются единственными файлами проекта.

Последствия: manual import становится основным понятным happy path MVP, а не
конструктором исправления парсера силами пользователя. Новая официальная версия
provider format требует отдельной structural fixture и regression-проверки, но
не изменения canonical Ledger contract без необходимости.

Обычный Alfa XML-экспорт имеет корень `Report`, имя схемы `MyBroker` и поля
рендеринга `Textbox…`; это не тот же контракт, что XML «для импорта» с корнем
`report_broker`. Наблюдённый обычный файл за короткий период недостаточен для
надёжного восстановления ledger mapping всех возможных строк. Adapter явно
распознаёт этот вариант как `alfa_xml_variant_unsupported`, а frontend предлагает
выбрать «XML для импорта». Это намеренная защита от выдуманного сопоставления
финансовых колонок, а не generic ошибка формата.

## ADR-046: Распределение сохраняет знаковые значения и не маскирует leverage

**Статус:** принято 28.08.2026 по результатам инспекции Phase 04.

Отрицательный денежный остаток, маржинальная задолженность или другая короткая
компонента могут привести к тому, что доля положительного актива превышает 100%,
а доля cash становится отрицательной. Это корректное знаковое распределение
относительно чистой стоимости портфеля, а не ошибка округления. Backend сохраняет
точные значения и их сумму, равную 100% при положительном известном знаменателе,
и добавляет диагностический признак отрицательной компоненты.

Круговая диаграмма не способна честно показать отрицательный сектор. Поэтому при
такой диагностике frontend не строит donut/pie и вместо него показывает понятное
пояснение и таблицу точных знаковых сумм и долей. Значения не нормализуются по
модулю, не обрезаются до диапазона 0–100% и не скрываются. Метрика cost basis в
пользовательском интерфейсе называется «Вложено в текущие позиции»: это
историческая стоимость приобретения остающихся позиций, а не текущая стоимость
портфеля и не сумма всех когда-либо внесённых средств.

Последствия: доли больше 100% и меньше 0% допустимы только вместе с явной
диагностикой; отсутствие диаграммы в этом состоянии является намеренным UX.
Расчёт остаётся на backend и передаётся frontend точными decimal-строками.

## ADR-047: Автоматические проверки изолированы от рабочей локальной базы

**Статус:** принято 28.08.2026 по результатам инспекции Phase 04.

PostgreSQL integration tests используют только отдельную базу `finance_test`.
Test bootstrap отклоняет URL, имя базы которого не содержит `test`, чтобы ошибка
в переменной окружения не могла очистить или наполнить рабочую базу `finance`.
Browser E2E запускает отдельный локальный стек: API на порту 8011, frontend на
5174, временное import storage и ту же изолированную test database. Runtime API
на 8000 и обычный frontend не являются E2E-целями.

Существующие synthetic записи, созданные прежней конфигурацией в рабочей
локальной базе, автоматически не удаляются: исправление окружения не должно
становиться скрытой деструктивной миграцией пользовательских данных. После этого
решения новые автоматические проверки не создают QA-портфели в runtime database.

Последствия: документация и команды проверок обязаны указывать `finance_test`;
попытка прогнать тесты против `finance` завершается до изменения данных. Удаление
старых локальных synthetic записей выполняется только как отдельная явно
подтверждённая операция.

## ADR-048: Автоматический FX и отдельные ручные QA-примеры

**Статус:** принято 12.09.2026 при исправлении ручного импорта.

Ранее worker выполнял FX-задания, но не создавал их по расписанию. Теперь
непрерывно работающий worker проверяет необходимость USD/RUB sync при старте
и каждые 60 секунд; минимальный период между заданиями по умолчанию — час.
Очередь остаётся PostgreSQL, конкурентная постановка API/worker сериализована
transaction advisory lock. В test environment и `--once` автоматическая постановка
отключена. Публичный источник не получает данные пользователей.

Последнее FX-задание читается отдельным GET endpoint, а не только по ID в памяти
браузера. В UI показан сохранённый курс; ручной ввод — свёрнутый fallback.
Автоматический FX не подменяет цены активов, не восстанавливает неизвестную
себестоимость и не делает ограниченную историю полной. Старые snapshots требуют
пересчёта. Значения partial/unavailable остаются честными.

Старые fixtures покрывают edge cases и не годятся как полный пример портфеля.
Для ручной проверки добавлен отдельный `docs/fixtures/manual_qa`, генерируемый
из вымышленного сценария с независимыми контрольными значениями. Структуры
соответствуют поддерживаемым provider layouts, но не объявляются спецификацией
всех официальных вариантов. Оригинальные отчёты в репозиторий не копируются.

В дополнение к ADR-047 браузерный стенд и regression tests разнесены по базам
`finance_browser_test` и `finance_regression_test`: browser imports создают общие
идентификаторы USDT и не должны ломать чистые API-сценарии. Старые базы не удаляются.

## ADR-049: Связанная Bybit-комиссия после execution при одном timestamp

**Статус:** принято 12.09.2026, исправление расчётной ошибки.

UUID-only tie-break мог списать комиссию в приобретаемом активе раньше самой
покупки. Это давало ложный negative_position и необратимо сбрасывало известную
себестоимость внутри расчёта. Прикладной слой теперь связывает asset fee с
crypto_trade только по точному source transaction ID, одному account/batch и
одинаковому occurred_at. Pure CalculationOperation получает необязательный
execution_operation_id; snapshot и operation effects обрабатывают execution
перед его комиссией. Несвязанные операции не переставляются по догадкам;
публичные Ledger payloads и timestamps не изменяются. Это исправление v2,
а не включение неизвестной стоимости Fiat/P2P в расчёт.

## ADR-050: Сводная диагностика считает затронутые позиции

**Статус:** принято 12.09.2026 после ручной проверки демо-портфеля в браузере.

Calculation snapshot сохраняет диагностику каждой операции для трассировки.
Повторная передача неизвестной basis между crypto assets может породить много
событий для одной позиции. Data-quality summary считает уникальные сочетания
code, severity, account и instrument, сохраняя исходные события в snapshot.
Для диагностики без instrument используется operation scope. Один инструмент
на разных счетах считается разными позициями.

Отсутствие market price влияет на current value, unrealised P&L и allocation,
но не на историческую basis или realised P&L. Неизвестная basis влияет на basis
и зависимые P&L, но не на отдельный income. Интерфейс объясняет необходимость
ручных цен и не предлагает восстанавливать basis текущей котировкой.
Финансовое ядро, Ledger и публичная форма JSON не меняются.

## ADR-051: Следующий этап — проверенные автоматические рыночные цены

**Статус:** принято 13.09.2026 по прямому выбору пользователя; реализация
предстоит в Phase 05.

После исправления критичных формулировок интерфейса следующим этапом выбран
модуль рыночных данных. Первый срез получает только публичные котировки
поддерживаемых акций/биржевых фондов Московской биржи и Bybit Spot через
существующий фоновый процесс. Автоматическая связь внутреннего инструмента с
внешним кодом допускается лишь при проверенной идентичности и единице цены.
Источники и условия использования проверяются до включения. Ручные цены
сохраняются; неоднозначные и неподдерживаемые активы остаются без
автоматической цены с понятной причиной.

Новая котировка может изменить текущую оценку и зависящий от неё
нереализованный P&L, но не восстанавливает неизвестную себестоимость, не
исправляет историю импорта и не переписывает Ledger. Фронт читает только
`/api/v1`; внешние запросы не содержат пользовательских финансовых данных.
Детальные границы и порядок реализации определены в `docs/PHASE_05.md` и
`docs/MARKET_DATA_DESIGN.md`.

## ADR-052: Автоматическое обновление без лишних действий и выбор источника по проверке

**Статус:** принято 13.09.2026 после обсуждения пользовательского сценария
Phase 05; уточняет ADR-051.

Пользователь не должен вручную запускать получение цен или ждать ответа
биржи при открытии портфеля. Фоновый процесс обновляет цены и пересчитывает
оценку по расписанию. Интерфейс сразу показывает последнюю сохранённую
оценку; новый результат появляется после фонового пересчёта. Основной экран
не содержит технических счётчиков, вида цены и нескольких временных меток.
Короткий признак неполноты виден только при наличии проблемы; подробное
происхождение цены и причина отсутствия доступны в деталях. Ручной ввод
остаётся способом исправить действительно отсутствующую цену, а не штатным
способом запустить синхронизацию.

Источник котировки не определяется местом импорта. Московская биржа ISS,
Bybit Spot и OKX Spot — кандидаты, которые надо сравнить по правам
использования, охвату, семантике цены, скорости и стабильности общего
снимка. Выбор конкретного адаптера до проверки не является принятым
решением. TradingView не использовать через парсинг сайта или неофициальный
интерфейс: опубликованная справка не предоставляет API для выдачи данных,
а условия ограничивают машинное использование. Если доступные кандидаты
не разрешают требуемый расчёт, оставить ручные цены и зафиксировать причину.

## ADR-053: Не включать внешние котировки без подтверждённых прав

**Статус:** принято 13.09.2026 для первого среза Phase 05; для CoinPaprika
уточнено ADR-056, для MOEX/OKX/Bybit ограничение сохраняется.

Проверены только официальные условия и документация кандидатов. [ISS MOEX](https://www.moex.com/a2193) даёт общедоступные задержанные данные для ознакомления; [политика рыночных данных](https://www.moex.com/files/4a1jy8j83qc25vv9p286tzsmc1) относит программную запись и арифметическую обработку к Non-display Usage, требующему договора. Наличие публичного URL не подтверждает право хранить цены и считать оценку портфеля. [OKX API Agreement, §9.4](https://www.okx.com/en-gb/help/okx-api-agreement) запрещает использовать даже публичные Market Data для финансового агрегатора/аналитической платформы. [Bybit API Terms, §6.6](https://www.bybit.com/common-static/compliance/legal/BYBIT/df1923006718fbba8ba70d7d762b9866.pdf) запрещают API benchmarking; право сохранять и показывать данные в этом агрегаторе из опубликованных условий не установлено. Поэтому повторные live-замеры скорости не проводились (0 из 3 для каждого кандидата) и ни один внешний адаптер не включается. Это отсутствие проверки, а не измеренная медленная работа.

Технические свойства сравнивались без запроса рыночных данных: [Bybit Spot tickers](https://bybit-exchange.github.io/docs/v5/market/tickers) дают общий снимок; `lastPrice` выражен в валюте пары, а `usdIndexPrice` — отдельный, иногда пустой USD-индекс. [OKX Spot tickers](https://app.okx.com/docs-v5/en/) дают общий снимок, `last` в котируемой валюте и `ts` генерации ticker; повторный запрос может вернуть более старый кеш. ISS охватывает российские площадки с задержкой, но конкретное поле цены одной акции/пая, валюту, время и board нельзя считать проверенными для адаптера без допустимого теста. USDT и USDC не считаются USD. Облигации, опционы и искусственные активы остаются без автоматического сопоставления.

Для MOEX, Bybit и OKX до подходящего договора/разрешения остаётся ручная цена.
На дату решения реестр live-источников был пуст; позднее ADR-056 выбрал
CoinPaprika после отдельной проверки прав, полей, единицы, времени и скорости.

## ADR-054: Автоматическая цена требует проверенного глобального сопоставления

**Статус:** принято 14.09.2026 как безопасная основа Phase 05.

Одного имени или тикера недостаточно для переноса внешней цены на канонический
инструмент. Таблица `market_mappings` связывает instrument с provider, market/board,
symbol, котируемой валютой, видом и единицей цены, качеством времени и подтверждённым
ISIN либо кодом криптоактива. Для `verified` обязателен источник подтверждения;
`ambiguous` и `unsupported` имеют причину и не дают автоматическую цену.
Приложение дополнительно проверяет текущий тип, валюту и идентификатор инструмента
при сохранении и выборе наблюдения, так что отзыв или изменение сопоставления
исключает цену из нового расчёта. Для криптоединицы первый срез допускает только
подтверждённый USD, не приравнивая USDT/USDC к USD. Облигации не включены.

Общий офлайн-снимок обрабатывается локально: сохраняются только точные наблюдения
проверенных инструментов, встречающихся в операциях портфелей. Одинаковый повтор
не меняет старую запись, конфликт значения под тем же ключом откатывает приём.
Пересчёт запускается через прикладной интерфейс только при изменении ссылки на
актуальную цену. Если пересчёт не удался после сохранения, повторный снимок
попробует его снова. Результат загрузки и сбой расчёта различаются в job
diagnostics. Публичный API предоставляет только просмотр сопоставления;
запись внешних цен остаётся внутренней. На момент принятия реестр live-источников
был пуст; ADR-056 позднее включил CoinPaprika в том же source-neutral контракте.

## ADR-055: Контекст использования рыночных данных — личный закрытый проект

**Статус:** принято 15.09.2026 по уточнению пользователя; уточняет оценку
применимости ADR-053, но не отменяет условия поставщиков.

Сервис разрабатывается как закрытый локальный некоммерческий pet project для
личного использования. Он не предлагается третьим лицам как платный продукт,
сервис котировок или публичная аналитическая платформа. При выборе источника
сравнивать официальные условия именно с этим фактическим сценарием и не
приписывать проекту несуществующую коммерческую модель.

При этом ограничения на программную запись и обработку данных, конкретную
цель использования, замеры API и принятие договора могут действовать и для
личного проекта. Например, §9.4 условий OKX ограничивает Market Data личной
торговлей и управлением счётом OKX и отдельно запрещает создание агрегатора
данных или аналитической платформы; отсутствие монетизации само по себе не
устраняет этот конфликт с расчётом стоимости активов из разных источников.
Поэтому заново проверить применимость каждого кандидата и искать подходящие
личному использованию альтернативы. До проверки условий, полей, единиц цены и
повторных замеров не включать live-адаптер или расписание.

## ADR-056: CoinPaprika Free как первый live-источник глобальных криптоцен

**Статус:** принято 15.09.2026 для закрытого личного некоммерческого проекта;
граница завершения Phase 05 позднее уточнена ADR-057.

[Условия CoinPaprika](https://coinpaprika.com/api-terms-of-use/) предоставляют
Free-лицензию на интеграцию API в некоммерческое приложение, не требуют ключа
и требуют видимый текст «Powered by Coinparika» размером не меньше 10 pt.
Опубликованные условия не задают отдельный срок локального хранения данных;
приложение сохраняет только минимальные наблюдения сопоставленных активов для
собственного расчёта, не публикует и не перепродаёт общий снимок. Изменение
условий поставщика потребует повторной проверки. При первом включении принятие
условий API санкционировано прямым разрешением пользователя использовать
ресурсы без дополнительного подтверждения.

[Общий `/v1/tickers`](https://docs.coinpaprika.com/api-reference/tickers/get-tickers-for-all-active-coins)
на Free охватывает до 2000 активов и обновляется в среднем раз в пять минут.
`quotes.USD.price` — глобальная агрегированная цена одной криптоединицы в USD,
а не последняя сделка пары Bybit и не цена в USDT; `last_updated` — время
обновления данных источника, не время сделки. Адаптер хранит их как
`global_aggregate` / `provider_snapshot`, отдельно от `fetched_at`. Для
USDT/USDC используется их собственная цена в USD, без приравнивания к доллару.
Пять reviewed идентичностей BTC, ETH, SOL, USDT и USDC заданы точными парами
канонического `crypto_asset_code` и CoinPaprika `coin_id`/имени. По совпадению
одного ticker сопоставление не создаётся. Если provider изменит id/symbol/name,
снимок отклоняется без замены последней корректной цены.

Три умеренных одинаковых локальных запроса общего снимка вернули HTTP 200 за
2,07 / 0,69 / 0,33 с и по 1 634 883 байта; ещё одна независимая серия дала
2,17 / 2,48 / 2,20 с и тот же объём. Это наблюдения из одного окружения с
кешированными ответами, не гарантия задержки. Worker делает один глобальный
запрос в час по умолчанию, с ограничением 15 с и 4 МиБ; даже 24 запроса в
сутки ниже [лимита Free 20 000 в месяц](https://docs.coinpaprika.com/api-reference/rest-api/introduction).
Пропуски, повторы, сбой источника и сбой пересчёта доступны как безопасный
status/counts в `/api/v1/market-data/sync/latest`. Браузер открывает сохранённую
оценку без запроса к CoinPaprika и тихо читает новый snapshot каждые 30 секунд.

Для MOEX [политика](https://www.moex.com/files/4a1jy8j83qc25vv9p286tzsmc1)
требует договор на программную обработку и накопление даже для личного
использования; [тариф Non-display](https://www.moex.com/s1147) одного рынка —
7 500 ₽/месяц без НДС. OKX ограничивает цель использования личной торговлей
и управлением счётом OKX, Bybit запрещает benchmarking; их доступность API
не снимает этих условий. Изученная альтернатива [Twelve Data](https://twelvedata.com/terms)
покрывает MISX, но Non-display разрешает только платный tier. Поэтому
автоматические цены российских акций и паёв пока не включены, ручные цены
сохранены. Нагрузочный прогон на отдельной временной PostgreSQL-базе записал
43 800 искусственных часовых observations пяти активов за 1,109 с; выбор пяти
последних цен занял 0,172 с, запись пяти новых цен с пересчётом одного портфеля
— 0,402 с. После 43 805 строк таблица с индексами занимала 18 956 288 байт.
Один общий HTTP-запрос выполняется отдельно, его время указано выше. Для
текущего локального среза автоматические observations остаются append-only без
истечения срока хранения: расчётные snapshot имеют `RESTRICT`-ссылки на
использованную цену, а измеренный годовой максимум пяти инструментов занимает
около 19 МБ. При росте до 1 млн строк или расширении охвата хранения правило
пересмотреть до введения очистки; нельзя удалять цену, связанную со snapshot.

## ADR-057: Phase 05 завершается криптоценами; account API выделяется в Phase 06

**Статус:** принято 16.09.2026 как граница Phase 05 и план Phase 06.

Автоматические цены российского фондового рынка не являются условием завершения
Phase 05. Для российских акций, фондов и облигаций сохраняется ручной ввод до
появления разрешённого и экономически оправданного источника. CoinPaprika worker
остаётся единственным live price adapter: он ежечасно сохраняет append-only
глобальные USD observations для присутствующих в портфелях BTC, ETH, SOL,
USDT и USDC. Накопленный ряд может
быть использован будущей исторической аналитикой, но не заменяет отсутствующие
операции, historical FX и corporate actions.

Phase 06 получает отдельную задачу read-only account connectors для одного
локального владельца. Connection привязывается к внутреннему broker/CEX
`account_id`; initial backfill проходит preview/confirm, последующий точный
incremental sync может выполняться автоматически. API executions, fees и
movements нормализуются в существующий Ledger. Positions и balances поставщика
сохраняются только как reconciliation snapshots и никогда не порождают скрытый
adjustment. Агрегированный provider P&L или «закрытая позиция» не подменяют
единый расчёт realised P&L из исполнений.

Pricing и account data остаются независимыми. Для публичных криптокотировок не
нужен пользовательский CEX key; приватный ключ понадобится только для личной
истории счёта. Не использовать личный аккаунт администратора как общий источник
для других пользователей. Первый срез не является multi-user SaaS: identity,
tenant isolation и сетевой deployment требуют отдельной фазы. Credential должен
иметь минимальные read-only права, храниться через `CredentialStore` вне БД в
открытом виде и никогда не попадать в frontend, logs или diagnostics. Trade и
withdraw permissions, заявки и вывод средств запрещены.

Подробный проверяемый план находится в `docs/PHASE_06.md`. Конкретные брокер и
CEX не выбираются фактом наличия файловых адаптеров: до реализации сравнить
официальные условия, методы, полноту истории, cursors, limits и sandbox каждого
кандидата.

## Открытые решения

- Хранение исходных файлов после локального прототипа.
- Канонический контракт переноса ценных бумаг и неизвестной себестоимости.
- Наблюдаемый provider-контракт Bybit deposit и fee в третьем asset, когда появится
  безопасный structural sample либо официально подтверждённая схема.
