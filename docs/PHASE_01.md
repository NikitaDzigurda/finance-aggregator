Проверено 2026-08-03: миграция `0004_import_staging` создала batch, raw rows и

защитила принадлежность batch составным ключом account+portfolio. Миграция успешно

JSON, согласованность account+portfolio и запрет повторного SHA-256 на одном счёте.

Раздел завершён 2026-08-03: исходные файлы сохраняются вне project tree под
случайным internal key с ограничением размера, allowlist расширений/content types,

реализует upload/status/preview/rows и не раскрывает storage key. Повторный файл на
том же account возвращает существующий batch без второго файла или job.

Versioned adapter registry запрещает повтор одной версии и не имеет доступа к
ledger. Миграция `0005_import_jobs` добавила очередь состояний
pending/running/succeeded/failed/cancelled; worker забирает задания через
`FOR UPDATE SKIP LOCKED`. Миграция прошла upgrade/downgrade/upgrade, а
`alembic check` не обнаружил расхождений. Сквозной PostgreSQL-сценарий проверил
безопасное filename, duplicate upload, file signature, job claim, реальный вызов
тестового адаптера, raw/normalized staging и warning preview. API, PostgreSQL и
worker успешно запущены через Docker Compose; health и OpenAPI ответили успешно.

## 7. Confirm, дедупликация и rollback

- [x] Реализовать fingerprint и внешние ID.
- [x] Реализовать атомарный confirm.
- [x] Сделать повторный confirm идемпотентным.
- [x] Связать операции с batch/row.
- [x] Реализовать rollback одного импорта.
- [x] Не затрагивать ручные операции и другие batch.

### Обязательные проверки

- [x] Двойной confirm не создаёт дубликаты.
- [x] Повторная загрузка обнаруживается.
- [x] Rollback возвращает ledger в исходное состояние.
- [x] Ошибка посередине commit не оставляет частичный импорт.

Раздел завершён 2026-08-10: миграция `0006_import_deduplication` добавила
канонический fingerprint импортной операции и отдельный уникальный ключ
дедупликации в пределах счёта. При наличии external ID fingerprint учитывает
provider и тип создаваемой операции; без external ID используется точное
каноническое экономическое содержимое. Явно разрешённый дубль сохраняет исходный
fingerprint для последующего обнаружения, но получает отдельный уникальный ключ.

Review API поддерживает исключение строки, явное сопоставление инструмента и
осознанное разрешение дубля. Confirm блокирует batch и строки, повторно валидирует
кандидаты и создаёт ledger operations вместе со связями batch/row одной
транзакцией. Повторный confirm возвращает те же ID. Rollback идемпотентно удаляет
только операции выбранного batch, восстанавливает staging rows и запрещён, если на
импортную операцию уже ссылается correction operation.

Проверено 2026-08-10: Ruff, mypy и 34 быстрых теста прошли. На изолированном
PostgreSQL 15 миграция прошла `upgrade -> downgrade -> upgrade`, а `alembic check`
не обнаружил расхождений. Все 7 PostgreSQL-тестов прошли, включая двойной confirm,
повторный upload, дедупликацию по external ID, явное разрешение дубля, повторный
rollback, сохранность ручной операции и другого batch, а также полный откат
транзакции при ошибке внешнего ключа посередине confirm.

## 8. Расчёт позиций на Python

- [x] Определить чистый контракт расчётного ядра.
- [x] Рассчитать количество, денежные остатки и среднюю себестоимость.
- [x] Рассчитать realised/unrealised P&L по выбранной и документированной политике.
- [x] Разделить комиссии, налоги и income.
- [x] Создать endpoint пересчёта и получения позиций.
- [x] Сохранить диагностические ошибки при отрицательной позиции или отсутствии цены.

### Обязательные проверки

- [x] Эталонная последовательность buy -> buy -> partial sell.
- [x] Комиссия в отдельной валюте.
- [x] CEX trade с двумя активами.
- [x] Повторный пересчёт даёт тот же результат.

Раздел завершён 2026-08-10: чистое Python-ядро принимает неизменяемые
нормализованные operations, manual market prices и явную cost-basis policy, не
работает с HTTP или PostgreSQL и детерминированно возвращает positions, cash
balances, currency metrics и структурированные diagnostics. В первой версии
выбрана weighted-average себестоимость. Trade создаёт две ноги — количество
инструмента и денежный quote-остаток; этот же контракт проверен на CEX-счёте с
crypto instrument и USD quote.

Миграция `0007_portfolio_calculation` добавила точные ручные market prices и один
заменяемый calculation snapshot на портфель с позициями, денежными остатками и
раздельными fees/taxes/income/realised P&L по счёту и валюте. API поддерживает
`POST/GET /api/v1/prices`, `POST /api/v1/portfolios/{id}/positions/recalculate` и
`GET /api/v1/portfolios/{id}/positions`. Последняя цена выбирается не позднее
`as_of`; отсутствие цены, отрицательная позиция, неизвестная себестоимость и
несовпадение валют сохраняются как безопасные diagnostics.

Проверено 2026-08-10: Ruff, mypy и 38 быстрых тестов прошли. Эталон
`buy 10 @ 100 -> buy 10 @ 200 -> sell 5 @ 180` дал quantity `15`, average cost
`150`, realised P&L `150` и при цене `210` unrealised P&L `900`. Отдельно проверены
EUR fee, USD tax/income, CEX trade, отрицательная позиция и missing price. На
изолированном PostgreSQL 15 миграция прошла `upgrade -> downgrade -> upgrade`,
`alembic check` не обнаружил расхождений, все 8 PostgreSQL-тестов прошли, включая
точный и повторяемый API-пересчёт и чтение сохранённых diagnostics.

## 9. Оценка готовности C++

- [x] Зафиксировать стабильный вход/выход расчётного ядра.
- [x] Измерить расчёт на реалистичном искусственном наборе операций.
- [x] Решить, переносить ли ядро в C++ сейчас или после следующих импортных форматов.
- [x] Если перенос оправдан, создать pybind11-модуль и сверить его с Python на эталонных сценариях — условие не выполнено, модуль не создавался.

Не переносить код в C++ только ради использования C++. Нужны стабильный контракт и измеримая причина.

Раздел завершён 2026-08-10: контракт расчётного ядра закреплён как версия 1 и
описан отдельно от HTTP, ORM и импорта. Детерминированный benchmark моделирует 8
счетов, 250 инструментов, USD/EUR и смесь trade, fee, tax, income, cash movement
и currency exchange. На Python 3.13.13/macOS arm64 семь последовательных прогонов
после прогрева дали медиану 0,047 секунды для 10 тысяч, 0,166 секунды для 50 тысяч
и 0,316 секунды для 100 тысяч операций; полный результат каждого прогона совпал,
diagnostics отсутствовали.

Перенос в C++ отложен до следующих импортных форматов или фактического профиля,
который покажет расчётное ядро узким местом полного API-пересчёта. pybind11-модуль
не создавался: текущая скорость не даёт измеримой причины поддерживать вторую
реализацию точной десятичной арифметики. Методика, результаты и условия повторной
оценки зафиксированы в `docs/CALCULATION_CORE.md` и ADR-019.
