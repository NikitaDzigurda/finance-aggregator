# UX/UI brief: Finance Aggregator web v1

## 1. Назначение документа

Этот brief передаётся UX/UI-дизайнеру до реализации Phase 04. Он фиксирует
продуктовую правду, пользовательские сценарии, информационную архитектуру и
состояния интерфейса. Дизайнер определяет визуальный язык и готовит макеты; он не
изменяет финансовую методику и не придумывает отсутствующие backend-возможности.

Режим поверхности по терминологии UX: **Operate**. Это рабочий инструмент для
регулярного контроля личного инвестиционного капитала, а не маркетинговый сайт.

## 2. Пользователь и его задача

Основной пользователь — частный инвестор с активами у двух брокеров и/или на CEX.
Он не хочет передавать сервису логины и API-ключи, поэтому периодически загружает
официальные отчёты вручную.

Главный путь:

```text
создать портфель
  -> добавить broker/CEX account
  -> выбрать источник и загрузить файл(ы)
  -> дождаться разбора
  -> проверить preview и разрешить проблемы
  -> подтвердить импорт
  -> добавить недостающие prices/FX
  -> пересчитать портфель
  -> увидеть аналитику и её качество
```

Главный критерий успеха: пользователь без Swagger понимает, что уже учтено, что
не учтено, почему результат partial и какое безопасное действие требуется дальше.

## 3. Продуктовые ограничения, которые нельзя нарушать

- Frontend получает данные только из публичного `/api/v1`.
- Денежные значения, количества, цены, курсы и веса приходят как decimal strings.
- `null` означает недоступную метрику. Его нельзя показывать как `0`.
- `empty` и `unavailable` — разные состояния.
- Backend рассчитывает стоимость, P&L, coverage и actual allocation. Browser их
  не воспроизводит и не суммирует.
- RUB/USD — переключатель только актуальной аналитики. Исторические события
  остаются раздельными по исходной currency или asset.
- Временные ряды Phase 04 — cash flow, income, fees, taxes, turnover и realised
  P&L по событиям Ledger. Графика ежедневной стоимости портфеля и исторических
  котировок пока нет.
- Продукт не даёт советов, сигналов, прогнозов и предложений сделок.
- Тип `bank` существует технически, но не показывается в пользовательских flow.
- Интерфейс локальный и single-user: login, роли и облачный onboarding не нужны.

## 4. Информационная архитектура

### Постоянный app shell

- переключатель текущего портфеля;
- выбор RUB/USD для актуальных стоимостных экранов;
- индикатор свежести snapshot и качества данных;
- основная навигация;
- заметное действие `Добавить данные`.

### Основная навигация

1. **Обзор** — состояние, ключевые метрики, структура и ближайшие действия.
2. **Активы** — holdings с фильтрами и диагностикой на уровне позиции.
3. **Импорт** — новый импорт, активный процесс, история и rollback.
4. **Распределение** — фактические доли и категории.
5. **События** — единая поверхность с вкладками cash flow, income, costs,
   trading, а не четыре несвязанные страницы.
6. **Качество данных** — проблемы, влияние и provenance.

В меню портфеля или utility-разделе:

- broker/CEX accounts;
- справочник инструментов;
- ручные prices;
- FX и запуск синхронизации CBR;
- параметры портфеля.

## 5. Экранная карта и приоритет

### Release slice A — обязательный пользовательский результат

1. First-run/empty state и создание портфеля.
2. Создание broker или CEX account.
3. Import wizard со всеми review-состояниями.
4. Data readiness: missing prices/FX, ввод batch и пересчёт.
5. Overview dashboard, holdings и data-quality explanation.

### Release slice B — расширенная аналитика той же фазы

6. Breakdown и broker/CEX exposure.
7. Allocation categories и фактическое распределение.
8. Ledger event timelines.

Визуальную полировку нельзя использовать как причину задержать рабочий slice A.
При этом оба slice должны использовать одну систему компонентов и состояний.

## 6. Требования к ключевым экранам

### 6.1. Первый запуск

- Объяснить в одном абзаце: сервис работает с инвестиционными отчётами, не просит
  банковский пароль и не совершает операции.
- Поля портфеля: название и базовая валюта.
- Следующим шагом предложить добавить broker/CEX account, а не показывать пустой
  dashboard без контекста.
- После создания счёта вести к выбору источника импорта.

### 6.2. Import wizard

Шаги должны быть видимы и восстанавливаемы:

1. **Источник и счёт.** Т-Инвестиции, Альфа-Инвестиции, Bybit Spot или Universal
   broker CSV. Показать точный принимаемый формат.
2. **Файлы.** Для Bybit — checklist четырёх обязательных CSV и единая зона выбора;
   для брокеров — один XLSX/XML. Не просить пользователя собирать ZIP.
3. **Обработка.** Понятный polling state: uploaded/parsing/awaiting review/failed.
4. **Preview.** Период, полнота, reconciliation, counts, операции, warnings,
   duplicates и errors. Финансовые итоги не должны выглядеть как уже применённые.
5. **Review.** Фильтр проблемных строк; действия exclude, match instrument и
   allow duplicate. Создание инструмента может открываться внутри matching flow,
   после чего новый instrument сразу выбирается для строки.
6. **Confirm.** Явно сообщить, сколько операций попадёт в Ledger. Повторный
   confirm должен выглядеть как уже выполненное безопасное действие.
7. **Результат.** Пересчёт и переход к data readiness/overview.

Rollback — вторичное опасное действие. До подтверждения показать последствия:
операции этого batch будут удалены, а исходный файл и review сохранятся.

Не показывать пользователю storage key, SHA-256, UID Bybit или production raw
payload. Технический diagnostic code допустим как вторичная раскрываемая деталь,
но главным остаётся понятное сообщение.

### 6.3. Data readiness

Это отдельная рабочая поверхность или заметная панель на Overview, а не набор
разрозненных error toast.

- список позиций без цены с переходом к batch-вводу prices;
- missing/stale FX с действием `Обновить курс CBR` и ручным fallback;
- unknown basis и import completeness как объясняемые ограничения, а не поля,
  которые UI обещает автоматически исправить;
- snapshot stale с явным действием `Пересчитать`;
- после успешного исправления — обновление состояния и возврат к dashboard.

### 6.4. Overview

Первый viewport должен отвечать: **сколько известно, насколько этому можно
доверять и где находятся средства**.

Рекомендуемая иерархия:

1. название портфеля, reporting currency, valuation/snapshot time и freshness;
2. current value как главный показатель;
3. cost basis, realised P&L, unrealised P&L, income, fees и taxes;
4. coverage/quality рядом с конкретной метрикой, а не один глобальный цвет;
5. структура по категории/счёту и counterparty exposure;
6. краткий список требующих внимания проблем с прямыми действиями;
7. переход к holdings и подробному качеству данных.

Если current value partial, главный показатель формулируется как `Известная
стоимость`, рядом показываются included/excluded counts. Нельзя визуально выдавать
её за полную стоимость.

### 6.5. Holdings

Таблица должна поддерживать инструмент и cash в одной модели, но ясно различать
их. Минимальные колонки: актив, счёт/организация, категория, количество, исходная
валюта, cost basis, market value, realised/unrealised P&L и quality. Нужны фильтры
по счёту, типу и качеству, а также доступная карточка строки на узком экране.

Для `null` показывать `Недоступно` или длинное тире с объяснением, но не ноль.

### 6.6. Allocation

- Показать фактическую стоимость и actual weight каждой категории.
- Partial coverage должна быть заметна до диаграммы.
- Показать known denominator, included/excluded positions и причины исключения.
- Веса приходят от backend; browser не пересчитывает их по значениям таблицы.
- Редактор target plan, целевые доли и deviation не входят в MVP.
- Не использовать copy `Купить`, `Продать`, `Рекомендуем` или `Ребалансировать`.

### 6.7. События Ledger

- Одна страница с вкладками `Движение денег`, `Доход`, `Расходы`, `Торговля`.
- Фильтры периода, day/week/month, timezone, currency/asset и pagination series.
- Легенда обязана явно показывать unit каждой series; RUB, USD, BTC и другие
  assets нельзя складывать в одну линию.
- У любого графика есть табличное представление тех же buckets.
- Текстом объяснить, что это события, а не динамика стоимости портфеля.

### 6.8. Качество данных

Группировать diagnostics по влиянию и возможности действия:

- `Нужно действие` — missing prices/FX, unresolved review, stale snapshot;
- `Ограничение источника` — period report, unknown basis, reconciliation mismatch;
- `Информация о расчёте` — versions, as-of и observation timestamps.

Показывать severity, count и impacted metrics, но не формировать непрозрачный
процентный score. Provenance лучше разместить в раскрываемом блоке `Методика и
источники`.

## 7. Состояния, которые дизайнер обязан макетировать

Для Overview, Import и Holdings нужны отдельные варианты:

- first-run empty;
- loading/skeleton без скачков layout;
- complete;
- partial с известными значениями;
- unavailable;
- safe API error с retry;
- stale snapshot;
- import processing;
- import awaiting review;
- import failed;
- duplicate upload;
- confirm/rollback idempotent success;
- длинные названия инструментов и 18–24 знака после запятой.

Toast используется только как подтверждение краткого события. Ошибка, требующая
решения, должна оставаться на странице и не исчезать автоматически.

## 8. Визуальное направление

Утверждённой айдентики пока нет. Дизайнер предлагает 2–3 действительно разные
концепции первой рабочей поверхности и после выбора фиксирует одну систему.

Обязательные качества:

- спокойный, точный и профессиональный инструмент без образа трейдинг-терминала;
- высокая информационная плотность с ясной иерархией;
- нейтральная семантика: зелёный/красный не должны превращать результат в игру;
- выразительность строится на типографике, сетке, данных и деталях состояний, а не
  на случайных gradient/glass карточках;
- светлая или тёмная тема выбирается осознанно под длительную работу; обе темы в
  v1 не обязательны.

Нельзя копировать Snowball буквально, использовать его брендинг или воспроизводить
его layout один к одному. Допустимо перенять паттерны: выбор источника, пошаговый
upload, объяснение формата и быстрый переход к добавлению данных.

## 9. Responsive и accessibility

- Основной breakpoint — desktop/laptop; обязательна рабочая tablet-композиция.
- Mobile application и полноценная phone-оптимизация вне Phase 04, но экран не
  должен ломаться при узком browser viewport.
- WCAG 2.2 AA для текста и controls.
- Полная keyboard navigation, видимый focus, skip link и логичный tab order.
- Таблицы имеют headers и доступные названия; графики — текстовый summary и table.
- Цвет не является единственным носителем состояния или знака.
- Учитывать `prefers-reduced-motion`; motion только объясняет переход или статус.
- Интерфейс и copy v1 — русский; коды валют и тикеры не переводятся.

## 10. Форматирование данных

- Визуальное округление допустимо только как presentation с возможностью увидеть
  точное значение; исходная string не теряется.
- Currency symbol/код всегда виден. Для asset quantities показывается asset code.
- Знак P&L передаётся знаком, текстом/иконкой и цветом.
- Даты показываются в локальном понятном формате, а timezone доступна рядом с
  историческими фильтрами.
- `0`, `Нет данных`, `Недоступно` и `Не рассчитано` — разные подписи.

## 11. Компоненты для handoff

Дизайнер должен подготовить минимум:

- app shell, navigation, portfolio/currency switchers;
- metric block с complete/partial/unavailable вариантами;
- quality badge и persistent diagnostic panel;
- data table, filters, pagination и responsive row/card;
- chart + accessible table pair;
- stepper, upload dropzone и Bybit file checklist;
- import summary, row status и resolution controls;
- forms для portfolio/account/instrument и batch prices/FX;
- empty/loading/error/confirmation patterns;
- modal/drawer только там, где он не скрывает контекст сложного review.

## 12. Ожидаемые материалы от UX/UI-дизайнера

1. Sitemap и user flow основного пути.
2. Две-три концепции Overview first viewport; одна выбранная концепция.
3. High-fidelity desktop-макеты обязательного slice A.
4. Tablet-варианты Overview, Import review и Holdings.
5. Ключевые состояния из раздела 7, а не только идеальный complete dashboard.
6. Компонентная библиотека с tokens: color roles, typography, spacing, radius,
   borders/elevation, icons, focus и motion.
7. Interaction notes для polling, review, confirm, rollback, recalculation и
   currency switch.
8. Handoff с размерами/поведением компонентов и реальным русским copy.

В демонстрационных макетах используются только явно synthetic данные. Нельзя
вставлять реальные пользовательские отчёты, номера счетов или суммы.

## 13. Открытые решения дизайнера

- визуальный мир, палитра, гарнитуры и характер иконок;
- точная desktop grid и способ компактного представления metrics;
- chart library-agnostic форма breakdown/allocation;
- modal, drawer или отдельная route для создания инструмента из import review;
- оптимальная граница между Overview data-readiness panel и отдельным экраном
  качества данных.

Решения не должны менять API-семантику или добавлять функциональные обещания.
