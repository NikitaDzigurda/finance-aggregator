# Phase 06: read-only подключения инвестиционных счетов

## Цель и граница этапа

Уменьшить зависимость от ручной загрузки отчётов: владелец локальной установки
подключает свой брокерский или CEX-счёт в режиме чтения, а система по расписанию
получает исполнения сделок, комиссии и движения активов, нормализует их в тот же
канонический Ledger и сверяет рассчитанные позиции с контрольным снимком
поставщика.

Phase 06 не меняет источник рыночной оценки. Публичный pricing-контур отдельно
получает котировки; приватный account-контур получает только данные конкретного
счёта. Цена закрытия, публичная рыночная сделка и личное исполнение пользователя
остаются разными сущностями.

Первый срез остаётся локальным и однопользовательским: «пользователь» означает
владельца установки, а подключение привязывается к конкретному внутреннему
`account_id`. Общий администраторский брокерский/CEX-ключ для обслуживания чужих
портфелей запрещён. Multi-user authentication, SaaS deployment и передача
котировок третьим лицам требуют отдельного проектирования.

Кандидаты первого среза — один брокерский API для российских акций и один CEX
Spot API. Наличие файлового адаптера Т‑Инвестиций или Bybit не выбирает API
поставщика заранее: перед реализацией сравнить официальные условия, read-only
права, полноту истории, курсоры, лимиты, исправления и тестовый контур.

## Условия начала

- Phase 05 сохраняет проверенные криптоцены как append-only observations;
  российские бумаги продолжают использовать ручные цены.
- Существующие файловые импорты, ручные операции и публичный `/api/v1` остаются
  совместимыми. API sync использует тот же staging/normalization/confirm contract,
  а не отдельный Ledger.
- Торговые поручения, вывод средств и приватные ключи с такими правами не входят
  в этап.
- До реализации выбрать локальную модель хранения секретов. Секрет не должен
  возвращаться из API, попадать в PostgreSQL backup в открытом виде, frontend,
  логи, traces или diagnostic payloads.

## 1. Проверить официальные API и выбрать первый брокер и CEX

- [ ] Сравнить официальные брокерские API, включая T‑Invest, Finam Trade API и
  ALOR OpenAPI: право личного автоматического использования, необходимость
  счёта, read-only scopes, доступность исполнений, комиссий, денежных движений,
  корпоративных действий, позиций, пагинации и исторической глубины.
- [ ] Сравнить официальные CEX API для Spot-счёта: сделки/fills, комиссии в
  отдельном активе, депозиты, выводы, внутренние transfers, rewards/P2P/earn,
  остатки, субсчета, курсоры, исправления и срок доступной истории.
- [ ] Для каждого кандидата отделить публичные Market Data endpoints от
  приватных Account endpoints. Не получать цены через приватный ключ, если
  пригодный публичный источник уже покрывает инструмент.
- [ ] Зафиксировать в `docs/DECISIONS.md` выбранные API, разрешённые методы,
  минимальные scopes, лимиты, глубину backfill и неподдерживаемые события.
  Файловый источник операций не должен заранее определять источник API или цены.
- [ ] Проверить ответы и скорость на synthetic/sandbox контуре. Реальные
  пользовательские ключи, номера счетов и финансовые значения не сохранять в
  fixtures, логах или документации.

**Готово, когда:** выбран по одному источнику каждого типа с документированным
правом использования и таблицей «метод API → исходное событие → Ledger event или
reconciliation-only snapshot».

## 2. Ввести безопасную модель подключения

- [ ] Добавить сущность connection, привязанную к внутреннему `account_id`, с
  provider, внешним непрозрачным account reference, состоянием, временем
  проверки, временем последнего успеха и ссылкой на секрет в `CredentialStore`.
- [ ] Реализовать интерфейс `CredentialStore`; выбрать локальный backend с
  шифрованием/системным хранилищем ключей. Ключ расшифрования хранить отдельно
  от БД. Не возвращать secret после записи и не подставлять его в exception text.
- [ ] При подключении проверять минимальные read-only permissions. Если provider
  позволяет определить scopes, отклонять либо явно блокировать ключ с правом
  торговли или вывода. Не реализовывать методы размещения/отмены заявок.
- [ ] Разрешить проверить, приостановить, переподключить и удалить credential.
  Отключение не удаляет уже подтверждённые Ledger events и их provenance.
- [ ] Ограничить исходящие адреса официальными provider hosts, добавить timeout,
  response limits, rate limiting, backoff и безопасные коды ошибок.
- [ ] Не считать этот локальный connection contract готовой multi-user моделью.
  Перед сетевым deployment отдельно спроектировать identity, authorization,
  tenant isolation, audit и восстановление ключей.

**Готово, когда:** компрометация frontend или дампа БД сама по себе не раскрывает
credential, а приложение технически не умеет торговать или выводить активы.

## 3. Сделать трассируемую и идемпотентную синхронизацию

- [ ] Расширить PostgreSQL job queue типом account sync с `connection_id`,
  режимами initial backfill/incremental/retry и запретом параллельной обработки
  одного подключения.
- [ ] Ввести sync run, cursor/watermark и bounded overlap window. Обрыв страницы
  не продвигает watermark; повтор после сбоя не создаёт дубликаты.
- [ ] Сохранять минимальный трассируемый source record: provider event ID,
  тип, provider timestamp, received_at, версию адаптера, hash и очищенный raw
  payload либо ссылку на зашифрованный объект. Не логировать полный ответ.
- [ ] Использовать устойчивый source key из provider/account/event ID. При
  отсутствии стабильного ID применять документированный fingerprint с теми же
  правилами overlap deduplication, что у файловых импортов.
- [ ] Обрабатывать отмены и исправления как новую версию/superseding event;
  подтверждённую финансовую историю не редактировать молча.
- [ ] Initial backfill отправлять в preview и требовать одного подтверждения.
  После явного включения connection точные incremental события могут
  подтверждаться автоматически; неоднозначные строки остаются в review.

**Готово, когда:** повторный backfill, overlap страниц, restart worker и
исправление provider не удваивают операции и не теряют трассируемость.

## 4. Нормализовать брокерские и CEX-события в общий Ledger

- [ ] Для брокера поддержать исполнения buy/sell, фактические комиссии,
  дивиденды/купоны/налоги и внешние денежные вводы/выводы только при наличии
  точного официального контракта. Заявка без исполнения не является сделкой.
- [ ] Для CEX первого среза ограничиться Spot fills, фактическим fee asset,
  депозитами, выводами и доказуемыми внутренними transfers. Margin, futures,
  options, earn, staking, P2P и rewards не угадывать.
- [ ] Не импортировать provider P&L или агрегированную «закрытую позицию» как
  каноническую прибыль. Ledger хранит исполнения и движения, а realised P&L
  рассчитывает единое финансовое ядро по принятой методике.
- [ ] Сопоставлять инструменты по устойчивым идентификаторам: ISIN + площадка/
  режим для бумаг; provider asset ID либо blockchain + contract address для
  токенов. Один ticker не создаёт автоматическое соответствие.
- [ ] Не смешивать операции разных субсчетов. Если transfer виден с обеих сторон,
  связывать ноги и не считать его внешним вводом/выводом дважды.
- [ ] Сохранить совместимость дедупликации API и файлового отчёта одного периода:
  повторная операция из другого transport должна распознаваться либо явно
  попадать в review, а не удваивать Ledger.

**Готово, когда:** API и файл одного provider дают совместимый Ledger, а
неподдерживаемое событие остаётся видимым и не превращается в финансовую операцию.

## 5. Использовать позиции и балансы только для сверки

- [ ] Сохранять provider balance/position snapshot отдельно от Ledger с точным
  `as_of`, provider timestamp и scope полноты.
- [ ] Сравнивать рассчитанные количества и денежные остатки со snapshot по
  инструменту/активу и счёту. Не создавать скрытые balance adjustments для
  устранения расхождения.
- [ ] Различать pending settlement, заблокированные средства, open orders,
  недоступную историю, неизвестный fee asset и действительно пропущенные события.
- [ ] Публиковать безопасные diagnostics и counts без токенов, внешних номеров
  счетов, raw payloads и персональных финансовых значений.
- [ ] При расхождении сохранять последнюю корректную историю, останавливать
  автоматический confirm неоднозначных событий и предлагать review/backfill.

**Готово, когда:** внешний остаток подтверждает полноту, но никогда не подменяет
необъяснённую историю искусственной операцией.

## 6. Автоматизировать обновление без скрытого риска

- [ ] После initial confirm запускать incremental sync по расписанию с учётом
  provider rate limits. Открытие страницы не ждёт provider и показывает
  последний сохранённый результат.
- [ ] После новых подтверждённых операций пересчитывать только затронутый
  портфель; pricing sync остаётся отдельным заданием.
- [ ] На основном экране показывать короткое состояние подключения и время
  последнего успешного обновления. Полные счётчики, cursor и причины ошибок
  оставить в деталях подключения.
- [ ] Показать понятные состояния: работает, требуется переподключение,
  ограничена глубина истории, ожидает проверки, расхождение, временный сбой.
- [ ] Уведомлять о необходимости действия только при истёкшем credential,
  постоянном расхождении или неподдерживаемом событии; временный retry не должен
  создавать навязчивые сообщения.

**Готово, когда:** после первоначального подключения новые поддерживаемые события
появляются без загрузки файла, а сбой API не портит последнюю оценку.

## 7. Подготовить данные для будущей исторической аналитики

- [ ] Сохранить точные `occurred_at`/precision всех API events и не заменять их
  временем получения. Зафиксировать границы доступного provider backfill.
- [ ] Продолжать append-only сбор проверенных CoinPaprika observations; не
  смешивать глобальную агрегированную цену с CEX trade price или исполнением
  пользователя.
- [ ] Описать coverage для исторического среза: наличие операций до даты,
  цены инструмента, FX, corporate actions и неизвестной себестоимости.
- [ ] Не строить непрерывный график стоимости из текущих цен и сегодняшнего
  состава портфеля. Historical valuation должен воспроизводить Ledger и выбирать
  только observations `observed_at <= as_of`.
- [ ] Вынести полноценный portfolio value chart, backfill исторических цен,
  TWR/XIRR и сравнительные индексы в отдельную фазу после проверки полноты API
  истории. Phase 06 должна предоставить измеримый readiness contract.

**Готово, когда:** система может объяснить, за какой период данных достаточно
для будущего графика, не дорисовывая отсутствующую историю.

## 8. Проверить и завершить этап

- [ ] Использовать только synthetic/sandbox fixtures и отдельные PostgreSQL-базы.
  Настоящие credentials и ответы пользователя не помещать в репозиторий.
- [ ] Проверить несколько зон высокого риска: permission rejection, cursor retry,
  overlap API/file deduplication, fee asset, двусторонний transfer, исправление
  provider, reconciliation mismatch и отсутствие скрытого adjustment.
- [ ] Пройти один браузерный сценарий: подключение synthetic provider, initial
  preview/confirm, фоновый incremental sync, пересчёт, расхождение и disconnect.
- [ ] Выполнить миграционный цикл, Ruff/mypy, финансовые/API-тесты, OpenAPI и
  frontend lint/typecheck/build. Проверить отсутствие секретов в логах, БД,
  diagnostics, frontend bundle и error responses.
- [ ] Обновить README, PRODUCT_SPEC, ARCHITECTURE, IMPORT_DESIGN, RUNBOOK,
  LIMITATIONS, DECISIONS и этот файл только по фактически проверенному результату.

## Что не входит

Торговые поручения, отмена заявок, вывод средств, ключи с trade/withdraw scopes,
автоматическое исправление остатков, margin/derivatives, кошельки и DeFi,
публичная ретрансляция котировок, multi-user SaaS, mobile, налоговая отчётность,
инвестиционные рекомендации и полноценный график исторической стоимости.
